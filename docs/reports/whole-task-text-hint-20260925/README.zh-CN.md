日期：2026-09-25。此轮紧随 [v18 完整任务对照](../whole-task-v18-20260925/README.zh-CN.md)，保留前一轮全部负面结果。

**4 次任务全部通过独立验收；插件组任务总耗时减少 38.36%，GPT 总 token 减少 40.40%。两对均更快。第二对费用记录完整，GPT + Jev API 等价估算费用减少 13.77%。第一对有一次 Jev 超时，用量未知，所以整轮准确费用节省率暂不成立。**

## 修了什么

原自动提示需要至少 8 个文件，且不识别 Analyze/分析。用户要求分析单个大日志时，普通 Codex 会直接读取完整文件；后续再筛选已经无法收回上下文开销。

修正后：明确提到的 16–100 kB `.log` / `.txt` / `.md` 文件也可以触发短提示。检查只读取文件名与大小，不读取正文、不调用模型、不改写原生命令。先选足够的本地检索，需要语义筛选时再用 `jev_evidence prepare`；保留原文恢复、覆盖限制、用户关闭开关及工具可用性检查。代码、结构化文件、小文本和明确要求原样输出的任务不会走这个单文件提示。

## 冻结设计

同一 GPT-6 Sol、初始 high、原生 `0.155.0-alpha.16.4`，两次重复、两组，顺序为裸/插件、插件/裸，单并发。插件候选版本 `0.2.0+codex.20260925130941`；运行前固定源码与输入哈希。沿用 540 行日志和相同独立判定，包括全部 8 个证据 ID、根因、排除假设、失败率、缓解后结果及未知结算影响。原始日志不得改变。

本轮没有强制调用 Jev，仍是正常任务提示。任务本身是已知回归用例；四次完成后停止，没有为填补超时用量重新抽一个好样本。协议里的停止规则指任务级超时/基础设施失败，任务内部成功回退的 Jev 请求也按实际失败保留。

## 自动化实际上做了什么

- 两次单文件提示提交都有事件记录。仅有 hook 回执不等于模型已经消费提示；本次同时观察到两次执行轨迹都改变为先局部查询、再排除已识别的常规行，没有先完整展示整份日志，且交付成果通过独立核验。
- 两次都没有调用语义筛选工具，证据 prepare/select 调用为 0。这里的改善属于插件引导的本地检索和完整工作流表现，**不能宣传成 Jev 语义筛选模型单独加速 38%**。
- 8 次真实 Jev 路由请求：7 次成功、1 次超时；两次 high → low 原生 `applied`。超时后另有一次 low → high 基准恢复，不算作额外成功判档，也不隐去其 2 秒等待。
- Jev 已知输入 12,564、输出 742 token；已知费用 $0.000527688。超时请求没有响应 token，用量记为 unknown，未当作零。
- 第一轮查询仍含匹配所有行的 `L[0-9]+`，所以先读了 100 / 90 行局部样本，再识别常规行做排除，仍有优化余地。最终完整结论依靠原始证据和独立 oracle；不能把任意关键词未命中当作“没有其他相关证据”。

## 交付阶段的 Windows 回归修复

首次 CI：macOS/Linux 通过，Windows 的自动检查点用例缺失文件哈希。旧实现吞掉了 Git 查询失败原因，因此不能确认超时是唯一根因。已将 Windows 后台 Git 查询时限从 500 ms 调整为 2 s，保留其他平台 500 ms；工作仍在任务完成后异步执行，不增加模型生成前的等待。增加 timeout/output-limit/unavailable 诊断与两项回归，最终本机 351/351 通过。此改动晚于上述付费对照，不冒充它已经经过新的 Windows 桌面性能测量。
