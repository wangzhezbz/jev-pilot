# Chrome / Computer Use 连续宿主会话验收

2026-09-24。本轮补上真正运行在官方 Chrome / Computer Use JS 宿主内的连续会话，并首次记录当前桌面任务里逐步 Codex 与连续 Jev 的操作段对照。**正常预算下，两端都观察到收益；Computer Use 的另一次预算耗尽样本反而变慢。样本不足以宣布稳定加速。**

## 已实现

- 一个宿主工具调用内观察、判断、执行多步，减少中间返回 GPT 的次数。使用现有官方插件句柄，不另开浏览器驱动或判断服务。
- Codex 提供业务子目标，Jev 只选择当前观察中的控件；整体目标、对象约束和最终证据留在宿主检查。保留有限历史，可在 Codex 接管后续跑。
- Chrome 每次核对来源；Computer Use 必须限定实际应用视图。新鲜观察、单次票据、重复/禁用控件、无进展、错误身份、超时、取消和执行不确定均有退出路径。
- 接管后页面未改变，不再花钱重复问同一含混判断。概率阈值只是保守接管条件，不保证正确。
- 官方 JS 宿主没有全局 `process`，已修复 Store/凭据读取的兼容性；专用 fetch 传输复用宿主网络，不在浏览器网页中放密钥。
- 默认宿主网络请求至少需要 1 秒可用预算，剩余不足在收费调用之前交回 Codex。其他调用方保留原准入规则。
- 插件 skill 增加普通多步浏览任务入口，由 agent 自行调用；用户不需要建立任务文件、启动脚本或另装 Jev skill。这不是拦截所有浏览器调用。

当前连续适配器支持可访问性控件点击。输入、滚动、坐标、视觉理解及敏感操作仍由 Codex 按官方宿主规则完成，然后可续跑。macOS 实机验收不能替代 Windows/Linux 实机验证。

## 当前桌面会话中的实测

| 宿主与操作段 | Codex 逐步处理 | 连续 Jev，含接管 | 观察结果 |
|---|---:|---:|---|
| Chrome：从首页完成六步结账故障调查 | 40.36 秒，6 次决策工具调用 | 11.06 秒，1 次调用 | 快 72.61%，约 3.65 倍 |
| Computer Use / Safari：从未解决列表完成四步调查 | 26.54 秒，4 次调用 | 33.39 秒，3 次调用 | 慢 25.84%；一次 Jev 超时，Codex 补做两步 |
| Computer Use / Safari：正常预算，从首页完成六步调查 | 40.47 秒，6 次调用 | 28.87 秒，1 次调用 | 快 28.65%，约 1.40 倍，无接管 |

三组最终结果均正确，未触发合成页面的任何修改操作。Chrome 的 Jev 循环本身是 3.21 秒，但**不能拿 3.21 秒直接对比包含 GPT 响应的 40.36 秒**；表中自动组 11.06 秒也包括发起循环的那次 GPT 响应。正常预算 Computer Use 的循环是 5.29 秒；实际操作段仍花了 28.87 秒，其中约 23.58 秒在循环之外，主要是发起工具调用前的 Codex 响应阶段。主模型等待仍会影响总时延。

Chrome 操作段 GPT 总 token 少 82.95%，非缓存输入少 81.24%。这是原生 `token_usage_record` 中对应决策工具调用的实际统计，不是字符估算。多数输入是长会话中的缓存重复读取，**不等于节省 82.95% 费用或订阅额度**。Computer Use 的 GPT 总量虽少，输出却增加，时间也变长；失败请求的 Jev 用量未知，不能按零计费。

补充的正常预算 Computer Use 六步对照：GPT 输入 **999,717 → 169,260**，其中缓存输入 **996,608 → 168,576**，非缓存输入 **3,109 → 684**；输出 **719 → 223**；GPT 总 token **1,000,436 → 169,483**，少 **83.06%**。自动组另有 6 次 Jev 请求，输入 **4,854**、输出 **264** token，无未知用量。两组最终结果一致。

### 测量边界

Chrome 一对、Computer Use 两对不同长度的已知合成用例，同一已有长会话、固定先 Codex 后 Jev，未盲测、未随机化顺序。每种条件只有一次，不能合并成重复样本置信区间。测量从起点观察开始，到最终 UI 读取结束；排除了之前的规划、会话构造、准备页面和之后独立验收。Codex 对照采用逐步观察决策；它本来也能批量执行已知动作，因此不能把该对照当成最佳原生实现。两端已经预热，不代表首次安装或冷启动。

Computer Use 四步自动组接在多轮诊断之后，共享任务网络预算已近耗尽；该组是故障诊断数据，**不是预算条件平衡的性能对照**。补充六步自动组在默认小时窗口自然进入下一窗口后开始，现场记录初始调用和累计耗时均为 0，使用同一任务 ID、同一默认预算和正式安装 helper。没有删除失败、手动重置任务 ID、提高预算或用补测覆盖失败值。不能从这些小样本推导产品全任务收益，更不能直接发布“稳定省八成”“两个宿主数倍加速”的宣传。

原生用量提取只保留被标记工具调用对应的实际记录；不导出完整对话、密钥或账户信息。可复核数据：[segment-usage.json](segment-usage.json)，提取脚本：[host-segment-report.py](../../../scripts/acceptance/host-segment-report.py)。

## 暴露的问题及整改

**完整目标与当前分支冲突。** 初版把整项任务和子目标同时交给 Jev，身份故障选了部署分支，5 次调用后由身份约束拦截。[失败原始记录](chrome-initial-failed.json) 保留。改为当前子目标后，Chrome 与 Computer Use 在该分支都选择低把握接管，未继续错误导航。仅缩短提示没有证明语义判断已可靠：需要 Codex 接管认证分支。

**接管不应重头开始。** Computer Use 身份故障由 Codex 点击认证事件后，同一会话续跑两步，正确到达 INC-401 / k17 的会话恢复预览；独立读取核验通过。[续跑记录](cua-identity-resumed.json)。普通结账故障两端完整六步均通过；Chrome 一次 5.85 秒、Computer Use 一次 6.21 秒均只是循环耗时，不是完整任务 A/B。

**预算尾段仍发网络请求。** 整个真实任务每窗口 20 秒累计网络预算中，4 秒保留给紧急操作。本轮累计诊断占满可用 16 秒，最后一次只获约 268 毫秒额度，发出后超时。[预算及日志](quota-timeout.json) 确认累计 `elapsedMs=16000`，并非猜测网络慢。现已增加宿主请求 1 秒最小准入；针对原先 268 毫秒剩余的回归验证不发请求、不增加 calls。现场已耗尽预算时也验证了 0 请求、0 点击、约 72 毫秒交回 Codex；现场触发的是原有保留预算检查，不能把它冒充新增 1 秒规则的独立实测。

失败请求与初始化失败都保留：初始化 `process` 兼容错误未发 API；本轮含正常预算补测合计 **42 次实际 Jev 请求**，已知输入 **34,451**、输出 **1,804** token，其中 **1 次超时用量未知**。详见 [validation.json](validation.json)。开发与诊断消耗不混入单个产品操作段。
