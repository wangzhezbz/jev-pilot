# 历轮优化复查：功能不能换成漂亮的节省数字

2026-09-23。基线 `9a9960e1258a260dabf8e07c87e031d2079bbd32`。沿路由、筛选、共享预算、并发、输出和技能入口追溯了 [23 条相关提交记录](reviewed-history.txt)，重点审查会改变工作流或减少可见证据的改动，结合当前代码、历史原始报告、反例及原生协议验证。它不是对全仓库每行代码的形式化证明。

**结论：此前既有真正有效的局部优化，也有功能回退和未补齐的保护。整体负收益的核心问题仍然是“Jev 增加了工作，却未稳定替代更多 GPT 工作”。需要先保住功能，再按替代掉的实际工作量验证净收益。不能保证每类任务都同时减少总 token 和时间。**

本轮没有主动新增付费模型实验；使用现有真实结果与免费的本地/合成端点验证。当前开发会话及后台正常调用另计。

输出跳过、服务故障或预算耗尽时，把原始工作交回 Codex，是降级；它与“辅助能力已经有效节省”是两回事。Chrome/CUA 的实际页面能力、本次未改动的功能不能仅靠入口保留宣称新一轮全部实机验收；本次没有重做真实 Chrome 页面操作。

## 二、本轮新确认并修复的两个证据问题

### 1. 状态仅放在字段里时，硬保护失效

反例：`{id:'a', text:'Settlement verification record', status:'pending'}`。正文没有 pending/失败等关键字，旧保护函数返回 false；若语义答案为 exclude，未完成项可以被丢弃。failed、in_progress、unknown 同样存在这个缺口。

修复：识别状态元数据。明确完成之外的非空状态保留供核验，不交给语义排除。该保护从早期 `2c18cf8` 的实现中就缺失，**不是上一轮新引入的回退**。

### 2. 去重只比较正文，丢掉不同观察的来源身份

反例：before.log 第 1 行、after.log 第 1 行、第 9 行都写着 `pool_limit=4`。它们可以说明不同时间/位置的状态，不能仅因正文一样就当同一条证据。旧 `against:['pool_limit=4']` 甚至会把这些带来源的候选全部当作已读。

修复：除候选 ID 外，正文和元数据共同参与重复判定；来源、行号、时间或状态有差异就保留。纯文本 `against` 只匹配无其他元数据的纯文本候选。确实相同的候选仍可去重，原文召回不变。

这也不是刚引入的问题：首版 `e2cf969` 就按正文去重。修复后某些日志的压缩率可能下降，因为原来误合并的独立观察必须保留。不能为了维持旧压缩率重新丢掉这些材料。对于缺少位置/时间元数据的重复纯文本，仍需用原始 artifact 和 duplicateIds 核验频次；后续可做保留全部来源的显式聚合，而不能把文本相同等同于事件相同。

新增的三项反例在修复前 **2 失败、1 通过**，修复后 **3/3 通过**。证据策略更新为 `preserve-uncertainty-v3`，路由策略仍为 v15，没有另改判档规则。

### 3. 核对一个看似可疑、实际正确的行为

取消旧筛选后暂不继续处理旧输出，初看可能像“用户插话后功能停了”。真实引擎探针表明：原生引擎先完成旧工具边界，再为插话触发新的 UserPromptSubmit；其后的大输出恢复筛选。此次保留了正确取消机制，没有为了增大筛选次数把旧输出按新目标处理。

证据：[插话恢复探针](steer-context.json)、[16 项原生检查](native.json)、[本地验证汇总](validation.json)。本地 **201/201** 测试通过，包含原有 198 项与新增 3 项；原生 16 项检查及新增插话检查通过。这不等于线上语义错误概率为零。

## 三、怎样才可能真正省：先定义“省掉了什么”

应分开报告四件事：GPT 总 token、GPT 缓存/未缓存输入与输出、Jev 用量、用户等待时间。账户额度另需账户可验证数据，不能从总 token 直接推出。

**把一万 token 交给便宜的 Jev，再让 GPT 读两千 token，可能降低 GPT 成本，但两者 token 简单相加未必减少。** 这叫工作转移，不能包装成总 token 必定下降。

判断是否值得增加一层的基本条件是：

> 被替代的 GPT 阅读、生成、工具等待和重试成本，大于 Jev 请求、插件说明、额外工具往返、召回和纠错成本。

时间还必须按关键路径算，不能把并行请求耗时之和当用户等待。质量验收必须相同。

旧干净对照里，自动组多了两次 GPT 生成，仅重复携带基线上下文就对应 +29,580 token；4 次 Jev 全部只是判断，没有切档或筛选应用。因此，应优先减少无必要的 GPT 往返，而不是再增加一个“是否值得使用 Jev”的 Jev 判断。

## 四、按优先级安排真正的收益路径

### P0：保护完成后，让辅助调用替代原来的读取

最有希望的场景是大量未解决的语义候选：许多搜索结果、跨文件候选、长日志中的不相关记录。精确文件名、数字计算、已读过的证据不需要再交给 Jev。

理想流程：正常一次读取/搜索 → 在正文进入 GPT 前完成候选筛选 → 返回足够作答的正文、来源与缺口 → 只召回缺失项。

需要避免：GPT 先读完整材料 → 再让 Jev 总结/筛选 → GPT 再读一遍。已经支付过的输入不会倒退；如果还多了一轮工具调用，负担会更大。

现有可用路径是同一个原生工具边界的输出替换，或用 `filter_output(path)`/`search` 替代原本的全量 `cat`。用户仍然普通对话，由插件和 Codex 选择操作。不能先要求用户自己写任务文件。

当前主要接入缺口是 code_mode/functions.exec 和复杂 MCP 结构化输出不在自动替换范围内。下一项应做**针对实际宿主结构的窄适配**，保留返回封装、错误、图片、引用和来源；只压缩可识别的文本字段。未知结构继续放行，不能用一个宽泛正则把对象改成字符串。

验收：同一原生读取是否少带入正文；GPT 生成次数是否不增加；必要证据是否完整；是否发生额外全量重读。先在合成端点验证真实出站内容，再做小规模真实任务对照。

### P1：批量与复用，降低每条判断的固定成本

已实现的同请求多候选、确定性去重、内容缓存和双请求并发应保留。重复判已读材料、额外 status 检查和重复全量 recall 应继续避免。

已有真实局部证据：相同请求的串行/双并发筛选各 4 次，平均 1,193 ms→655.25 ms，输入输出用量完全相同，全部通过预设质量检查，见 [原始结果](../parallel-filter-20260923/live-summary.json)。它说明这一个筛选部件可以缩短等待，**不是整个 Codex 提速 45%，也不是减少 token**。

下一步返回体还可将重复诊断/概率信息留在本地明细中，模型只接收正文、来源、必要的不确定状态和召回标识；但应先测实际原生出站体，并确认调用方没有依赖被移走的字段。不要直接删掉证据字段。

### P2：判档根据下一阶段，而不是反复看整个难题标题

路由看到“复杂并发修复”就持续建议高档，即使实现和检查已经结束，也可能错失收尾降档。应使用已观察到的任务阶段、最新失败、尚未完成的检查和原生 plan 状态来判**下一步**；输入不充分就保留当前档位。

保留 Jev 给出的复用期，失败/新输入/阶段变化提前重评，不能恢复无变化整轮停判。各模型需分别验证；低档导致更多错误、工具回合或返工，会抵消推理节省。

验收应比较固定用户档位、固定较低档位和自动路由三个组。若自动路由只与固定低档一样完成任务，却多花判档成本，它就没有证明动态判断的必要性。记录实际 applied 和出站参数，不能拿建议次数当收益。

### P3：降低网络和同步路径成本，但先测量

当前每次 TypeSafe 调用会启动 curl；连接没有跨请求复用。工具边界内路由与输出处理按顺序等待。它们是明确的架构成本，但没有分段数据证明它们占了旧实验剩余慢速的多少。

先记录启动、代理/连接、首字节、响应完成和宿主边界时间，再决定持久连接或路由/过滤并发。必须保留现有代理行为、取消、超时、共享预算、紧急判断优先和过期结果隔离。不能为了几百毫秒让 Chrome 联网或任务取消再次出问题。

### P4：真正的长会话压缩，优先使用原生能力

当前 `compact` 只是可恢复交接材料，不会缩短已经进入原生会话的历史；它不能兑现长期会话的“回收 token”。

本轮从本机 `codex-cli 0.155.0-alpha.9.2` 生成协议 schema，确认存在 `thread/compact/start`，必填 `threadId`。**只核对了接口存在，没有触发当前会话压缩，也没有验收它的收益。** 这提供了比直接改写会话文件更可行的研究入口。

后续应在隔离任务上验证：原生本已自动压缩的情况下是否仍有额外收益；压缩本身的模型成本；约束、待办、来源、最近错误和副作用是否保留；是否增加重新查找和解释。只在长上下文的预期后续收益足够覆盖压缩成本时考虑触发，不必每轮压缩。

## 五、下一次性能验证怎样避免再做无意义的大测试

1. 先免费验证实际接入：输出确实变小、出站档位确实改变、取消和回退正确。接入没有产生替代，就不先烧大量 GPT 测试。
2. 按模块做小型对照：裸 Codex、空载插件、仅筛选、仅路由、完整插件，主比较固定为裸 Codex；不同组禁用其余变化，不能用更慢的一组挑出漂亮差值。
3. 固定独立验收器，包含未完成状态、矛盾、不同来源的同文记录、无收益/全相关输入，以及服务失败。必需测试、失败样本和重试费用全部保留。
4. 记录新时间线、每次 GPT 用量和缓存、Jev 用量、生成次数、工具往返、召回量、实际替换/切档。对有希望的场景平衡顺序并重复，再报告配对方向和不确定范围。
5. 只发布实际覆盖场景的结论。如果只节省 GPT token、却耗时更长，要明确写出来；不能合称“又快又省”。用户普通使用方式保持不变，实验入口由开发验收使用。

本轮修复没有移除任何功能或操作，也没有修改模型/档位策略、代理、Chrome 驱动或用户原生历史。某些额外材料现在会被正确保留，这是保护功能的成本。是否已经获得整套净收益，仍需上述验收，不能由修复数量或 GitHub 项目数量推出。

安装状态见 [deployment.json](deployment.json)：修复已写入磁盘，当前进程与安装指纹不匹配，需下一次正常重启加载；未强制中断桌面任务。
