# 完整流程排查与 v14 修复

> 后续更正：本报告的无变化整轮/跨轮停判策略已在 [v15 功能审查](../functional-audit-20260923/README.zh-CN.md) 撤回，因为它会漏判新任务、阶段变化和失败。以下历史测量保留，不代表这些策略仍在使用。

2026-09-23。**仍未验证普遍省时、省 token。** 六次干净环境的真实 GPT 任务全部通过独立质量检查，但完整组相对原生组耗时观察值增加 26.04%，GPT 总 token 增加 8.68%。本次没有实际切档或自动过滤，也没有通过 MCP 替代语义工作，因此不能把任何差值解释为“切档带来的效果”。

## 本轮解决了什么

1. **无效收费判档。** 用户已在受支持最低档位时不调用 Jev。同一会话连续两轮各至少两次有效判档、但没有产生自动档位变化时，后两轮暂不收费判档，第五轮重新采样。模型、用户档位、工作目录变化，间隔超过五分钟或中途新输入，会重开评估；失败/中断的任务不用于训练退避。暂停时保持用户档位，不影响其他 Jev 操作。代价是可能错过暂停期间的一些降档机会。
2. **默认上下文和多余往返。** 技能正文从 6,898 字节降到 3,208 字节（减少 53.49%）；证据、工作流和状态操作分开按需读取。常用操作参数可直接查到，不再强制先做一次 status 调用。优先精确搜索；答案已找到、小任务或证据已读时不追加 Jev 判断。这些是说明体积/工作流改进，不直接等同于实测 token 节省。
3. **安装器复制整个开发目录。** 本地市场原来指向仓库工作目录，旧缓存约 157 MB，含历史实验数据库。隔离配置目录放入仓库后，原生安装器递归复制并报 File name too long。新增发布白名单暂存器，拒绝符号链接逃逸和仓库内目标，排除实验、凭证与运行状态；本机市场改指向约 17 MB 的干净目录。旧缓存保留；未发现其中有 `.env.local` 或 `auth.json` 文件。安装体积不代表推理加速。
4. **进程号复用误报。** 状态检查同时核对父子关系与启动时间，不再仅凭两个 PID 存活判断旧桥接仍在运行。无法核对时明确记录未知。
5. **实验污染。** 原生运行时仍可能加载全局插件，即使给出禁用覆盖。新试验使用仓库外私有 CODEX_HOME，经原生插件管理器安装，逐次在推理前核对 MCP 清单：原生/空载组为空，完整组只有一个 Jev 工具。没有注入技能正文，没有强制模型调用 Jev，也不强制完整读取日志。

## 原因与证据

- **本次收益路径没有发生。** 四次建议均未产生可执行的降档，实际变化 0，自动过滤 0，MCP 语义操作 0。不能因 Jev 被调用就算优化有效。
- **往返次数主导总输入。** 原生组共 11 次模型生成，完整组 13 次，空载组 14 次。每多一轮，都可能重新计入已有上下文。空载组无 Jev，却也明显慢于原生组，说明单次耗时比不能分离随机执行路径与适配层成本。
- **插件确有上下文税。** 完整组首轮输入分别比对应原生组多 929 / 908 token。一次没有实际委派的小任务也会承担工具/技能元数据开销。
- **缓存不能按“总 token”猜。** 原生未缓存输入 29,794，完整组 53,910（增加 80.94%）。完整组并发修复的第三次生成有 16,766 输入 token、缓存 0；该任务从未切档，不能归因于切档破坏缓存。单独的免费原生请求检查确认初始前缀保持一致，但它不能解释真实服务端缓存未命中的原因。
- **没有发现外层 MCP 双份正文。** 同时带 text 和 structuredContent 的探针中，原生模型请求里的标记出现一次。没有为这个未成立的猜测改产品。

因此，日志组少 6.60% GPT token 也不能宣称是 Jev 筛选的贡献；它没有做筛选，且该组反而更慢。此前的并行 Jev 微基准只能证明局部请求等待缩短，无法代替本报告的完整任务数据。
