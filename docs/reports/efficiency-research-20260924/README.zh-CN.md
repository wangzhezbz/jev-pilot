# 同时加速和省 token：源码研究与原生接入实验

2026-09-24。研究基线 `ef66f60372fb0515bf3f20370b41a88c9e596dee`。本轮核对 7 个公开仓库，重新计算已有真实任务记录，并执行 8 次本地模拟模型协议检查（4 次探索、4 次可复现检查）。没有新增收费 GPT/Jev 测试，没有修改已安装插件、全局配置或桌面路由策略。

## 结论与优先级

**最值得投入的是减少主模型往返和重复输入：一次取得足够的证据，在送入主模型之前处理，而不是给每个步骤再加一次 Jev 判断。** 这是由当前轨迹和上游实现支持的工程方向，尚不是完整任务净收益已经达标的结论。

此前把判档速度、输出体积和完整任务收益混在一起，会让局部优化看似成功，而用户仍然更慢。本轮确定了三件事：

1. 单靠继续加速筛选器，解释不了也消除不了现有几十秒的任务差异。需要改变主模型实际走的路径。
2. 全局改写 shell 命令虽然能缩小输出，但确实可能破坏 code-mode 程序读取原值。已经用当前原版 Codex 复现，因此不作为通用默认方案。
3. 已有的同一工具单元内“取原值—计算—精简展示”路径能保留原值、恢复原文，并让更短的输出真正到达模型，且不增加模型请求轮数。现在缺的是自然任务中稳定采用这条路径，以及完整任务的净收益验证。

重启核验：当前观察到的 MCP 服务全部加载 `0.2.0+codex.20260924150300`，详见 [activation.json](activation.json)。这不等于本任务发生了实际切档。

## 1. 现有实测告诉我们，收益到底被哪里吃掉

下面重新计算已有 `delegation-ab-20260924` 记录，**不是本轮新跑的成绩**。两组都使用 Astra high，功能验收通过。

| 配对 | 完整材料：时间 / 全部已知 token | Jev 筛选：时间 / GPT＋Jev token | 主模型生成次数：完整→筛选 |
|---|---:|---:|---:|
| 0 | 61.938 秒 / 90,750 | 128.561 秒 / 102,891 | 5→5 |
| 1 | 108.402 秒 / 135,836 | 63.238 秒 / 101,621 | 7→5 |

第一对只省了 1,125 个 GPT token，却多出 13,266 个 Jev token，净多 12,141。第二对少了两轮生成，GPT 少 47,481，加上 Jev 后净少 34,215。只有两个配对，不能据此把差异全部归因于筛选，也不能得出稳定平均收益；但它明确指向“是否少走主模型轮次”这个值得检验的变量。

两次筛选准备分别耗时 1.965 和 1.375 秒，任务却耗时 128.561 和 63.238 秒。即使理想地把准备时间降到零，也无法解释第一对多出的 66.623 秒。最新优化让组件快约一半，不能被包装成整个任务也快一半。

更具体的浪费：两次筛选组仍读取了 `review-evidence.md`，然后完整读取 `source-archive.md`。主模型重新看了一遍被筛掉的内容，筛选成本已经支付，输入削减的好处却被拿回去了。现在的覆盖说明和按条件回读可以帮助避免这种情况，但还没有自然任务实测证明它已解决。

这些运行首个请求约 15,204～15,218 个输入 token；另一组修复任务约 16,051～16,062。后续生成继续带上初始上下文和新增历史，因此少一轮请求可能比少显示几百字更有影响。这里的首轮输入是记账锚点，包含整个宿主上下文，不是 JevPilot 单独增加的开销；也不能将它直接当作下一次必然省下的额度。

另一个实测反例：固定 high 的修复任务 6 轮、165.369 秒；固定 medium 10 轮、194.300 秒，其中出现测试失败后的修复。较低 effort 没有保证更短路径。自动组还有一次始终 high、零实际切档的超时，不能把所有慢归咎于降档。

计算与输入文件哈希见 [derived.json](derived.json)。跨模型 token 相加用于回答“总数量是否下降”；费用和 Codex 订阅额度必须另算，缓存输入也不能按未缓存输入计价。

## 2. 七个仓库，具体借鉴什么

固定源码版本见 [sources.json](sources.json)。只读取源码和文档，没有运行第三方安装器、hook 或其他程序。

| 仓库 | 有价值的实现 | 放进 JevPilot 的条件 |
|---|---|---|
| [RTK](https://github.com/rtk-ai/rtk/tree/005eb9c54ca659d8c2df3004a218f3f025ee254a) | 按命令类型提取结果，保留错误和原文恢复；执行前改写 | 借鉴确定性格式处理；不能把任意 code-mode 命令全局包起来。其“最高 90%”针对 Bash 输出，token 估计使用字节换算，不是完整账单 |
| [context-mode](https://github.com/mksglu/context-mode/tree/5a92b7caaf0086d04b87cc03a82505c891aa8254) | 沙箱内处理、索引检索、批量执行 | 借鉴同次调用内处理；部分路由仅返回改用另一个工具的提示，会再加一轮主模型，不能直接照搬 |
| [CX](https://github.com/contextlimit/cx/tree/b7c81334e63ba3c1adaafbd2773ca2b8049ae7ae) | 针对已知命令的结构化呈现、退出码和完整输出契约 | 在展示层做可靠格式处理；计算、精确 JSON/CSV、代码和错误证据仍须保真 |
| [jev-codex-token-saver](https://github.com/jcressler/jev-codex-token-saver/tree/1e1214bd7a1d7b2d3ee32bf1b8a88bbf9cd9d820) | 小输入本地直通；候选先收窄；一次调查返回原文证据；有限补读 | 最值得借鉴的是降低调查往返。固定只留少数片段不适合“找出所有符合项”，不得照搬到穷尽分类 |
| [codex-context-diet](https://github.com/konstantinosbotonakis/codex-context-diet/tree/79670b247dbdc37203454675b8fb7a5269440e75) | 大输出门槛、摘要缓存、短恢复提示 | 借鉴准入与去重复；不能用重新执行原命令代替恢复已保存原文，也不能只凭 hook 返回值断言模型收到替换 |
| [Astra-Ares](https://github.com/miuuyy/Astra-Ares/tree/b2011446d88202329dcdc5163500ca818aba9dbb) | 原生 configuration update、按生成次数租约复用 | 保留同模型切档和稳定前缀；其 README 明确真实工作负载相对固定 effort 的节省尚未测量 |
| [codex-jev](https://github.com/yannip1234/codex-jev/tree/ff35965bba78ac9502424c1d9bc7877f382499a2) | 在 Codex fork 内处理工具结果和完整历史，保留调用/结果配对与近期内容 | 说明真正改历史需要宿主支持；自定义 fork 带来版本维护成本。不能把我们现有 handoff 宣称为原生历史压缩 |

其中最有参考意义的是同一项目的两份相反结果：

- [Evaluation v2](https://github.com/jcressler/jev-codex-token-saver/blob/1e1214bd7a1d7b2d3ee32bf1b8a88bbf9cd9d820/benchmarks/results/EVALUATION-V2-2026-09-19.md)：Jev 组相对 stock，Codex 输入少 4.6%、计入选择准备后的时间少 20.2%，工具调用 22→17。只有两个任务、每组两次；质量评分曾在已知分组后修正，不能当作独立盲评。
- [Controlled workflow](https://github.com/jcressler/jev-codex-token-saver/blob/1e1214bd7a1d7b2d3ee32bf1b8a88bbf9cd9d820/benchmarks/results/CONTROLLED-WORKFLOW-2026-09-19.md)：可执行验收全部通过，但相对 stock 输入多 0.23%、时间多 21%。其“省 37.2% 输入”比较的是更差的本地选择组。

这些不是“其他项目无效”的证据。它们说明：选对来源可以有用，但不保证整个任务更快；比较对象和往返路径必须一起看。

## 3. 当前原版 Codex 的新实验：哪里压缩才不会破坏功能

平台 macOS arm64，原版 `codex-cli 0.155.0-alpha.16.3`。本地 HTTP 服务提供模拟模型响应，Jev 判断也是模拟的。使用生产 evidence 实现及现有原版引擎验证脚本。隔离 CODEX_HOME 和工作目录；没有接触用户任务命令。

合成命令产生一条目标证据和 350 条噪声。程序可以先读取原值，检查退出码和 350 条记录，再决定给模型显示什么。执行前改写只匹配这个特定合成命令，并故意截取首行，测试是否会影响程序读取原值。

| 路径 | 模型可见输出字节 | 程序原值检查 | 原文恢复 | 主模型请求数 |
|---|---:|---|---|---:|
| 原始输出 | 25,452 | 通过 | 不适用 | 2 |
| 执行前改写，仅展示 | 252 | 未执行 | 未提供 | 2 |
| 相同改写，同时计算原值 | 302（错误输出） | **失败：RAW_RESULT_CHANGED** | 未提供 | 2 |
| 同次调用：计算用原值，展示用精简值 | 2,938 | **通过** | **逐字恢复通过** | 2 |

最后一路模型可见体积减少约 **88.46%**。初次探索为 2,939 字节，可复现检查为 2,938；包装中的运行元数据可变化，不是输出内容质量变化。初次记录见 [exploratory-probes.json](exploratory-probes.json)，正式结果见 [protocol-results.json](protocol-results.json)。

必须分清：这证明接入边界可行，不是实际 tokenizer 计数，不是付费模型速度测试，也没有证明真实模型会自动选择这条路径。模拟服务甚至会在工具报错后发出完成消息，所以 `nativeTurnCompleted=true` 不能当作功能通过；原值检查失败单独记为失败。

由此排除一个危险捷径：只为了接入自动化而全局包裹命令。管道还可能改变退出码、流式输出和审批语义。正确方向是在展示边界处理，保留原始计算值；无法确认边界时保持原结果。现有同次调用工具可实现这一点，但任意工具的透明拦截仍不是已完成能力。

复现（开发验证命令，不是用户正常使用步骤；需要本机 Codex 模型目录）：

```sh
node scripts/acceptance/pretool-rewrite-study.mjs --out=/tmp/jev-pretool-new-report
```

其他系统可通过 `JEV_PILOT_CODEX` 指定原版二进制；本轮只验证 macOS，不宣称 Windows/Linux 同样通过。

## 4. 接下来具体怎么实现，如何判断值不值得用

### 第一优先：把调查做成一次返回足够证据的只读入口

复用现有 `search`、`select`、`prepare`、`recall` 和原文存档。现在的 `search` 是单个字面查询加片段筛选，尚不等于完整的一次调查：需要补上多条有区分度的查询、同文件重叠片段合并、命中位置附近的必要上下文、明确的范围与缺口。

一次工具调用内完成：本地定位候选 → 确定性去重复/合并 → 仅对尚有语义歧义的大候选池调用 Jev → 返回原文证据、范围、源哈希和具体补读入口。避免先返回“请换工具”的提示；工具定义本身应足够使用，不加 status/skill 阅读前置轮次。

定位问题与穷尽筛选必须分开。前者可以返回少量高相关片段并明确不完整；后者必须保留所有命中和不确定项，不能用 top-k 冒充完整。读原文是正常恢复能力，不能为了数据好看禁止补读；应解决为什么已给的证据还不够。

### 第二优先：可确定处理的输出不再请 Jev 判断

为明确的测试/日志格式做展示处理：通过数量、失败原文、堆栈、被折叠重复记录的计数和原文定位。相同文本出现在不同时间、来源或状态，不能直接当作同一观察删掉。未知格式、精确输出、代码、图像、未结束命令默认保留。

缓存以源内容哈希、任务问题、策略版本及必要上下文为边界；来源变动即失效。只缓存独立判断，涉及跨条目关系不能拆成单条复用。现有缓存已有一部分能力，需要补上调查范围和回读的一致性，而不是另造一套缓存。

### 第三优先：继续保留判档，但用质量与净收益校准

当前自动判档功能保留。下一阶段的准入依据要从“可以问 Jev”转为“这个阶段存在可验证的净收益机会”。不能将遇到 high 不变一律视为无效，也不能将有切档就计作节省。按模型和阶段比较固定档位与自动档位，完整计入后续返工；不为降低数字擅自换弱模型或关闭功能。

### 验收标准先固定，再跑付费对照

先通过离线边界检查：原值、退出码、原文恢复、遗漏提示、失败回退正确；精简后的内容真正到达模型；不额外多出一轮“再换工具”。当前协议实验通过最后一种路径，但自然采用率仍待测。

随后使用未参与调参的新用例，比较三组：原生 Codex；相同调查工作流但仅本地处理；相同工作流加 Jev。模型、任务要求和质量判定一致。至少覆盖大规模语义证据、源码定位、多条失败混杂日志，以及小任务/精确 JSON 两类负对照。诊断阶段固定 effort，分离筛选贡献；最终还必须用默认判档加筛选的完整组合复验，不能只发布去掉路由成本的成绩。

同时统计完整任务时间、GPT 输入/缓存/输出、Jev 输入/输出、未知用量、生成轮数、回读和失败/重试；超时和失败不得删掉。首次运行与重复来源分别报告，不能只挑缓存暖了的结果。

用户要求的双目标是：质量不下降，完整任务时间减少，GPT＋Jev 的已知 token 总量也减少。具体任务组还应看配对方向和不确定性，不用一个漂亮均值盖住回退。费用按各模型实际价格另算，订阅额度没有原生账单证据就不承诺。

这轮没有更换桌面版本，也不需要再重启。研究产物是明确了下一步的实现重心，并用原版引擎排除了会破坏正常计算的自动化方案。**完整任务双指标改善仍然是待验收目标，不能将本轮 88.46% 的输出缩小写成产品省 token 或加速幅度。**
