# 缓存切档、路由预算与自然筛选复核

2026-09-24 · macOS · 原生 Codex `0.155.0-alpha.16.3` · 候选策略 `effort-v16-cache-budget`

**本报告验证修复机制和功能兼容，不是已经证明整体省时、省 token 的性能报告。** 六个模型真实任务验收通过；GPT‑6 Sol 的一次切档后缓存命中得到改善；自然筛选任务仍暴露了开销反例。前一轮 [12 次诊断](../factorial-20260924/README.zh-CN.md) 保持原样。

## 本次修改

| 问题 | 修改 | 验证范围 |
|---|---|---|
| 中途改变顶部 `reasoning.effort`，可能使服务端隐藏前缀改变 | 在经过验证的原生版本上启用原生 `reasoning_effort_override`。由 Codex 自己追加 `configuration_update`，保持顶部 effort；插件不拼接伪造消息、不改 TLS 流量 | 六模型原生请求捕获；六模型真实调用；原生压缩及压缩后续接 |
| 连续维持用户档位的判断过早消耗例行预算 | 连续两次有效、维持基准档位且建议间隔为 1 时，间隔延长到 2 个工具边界 | 下一边界仅复用一次；新输入、失败、新进展和到期仍重判；不延长自动降档；总调用上限和预留不变 |
| 工具定义没说明可以直接准备文件，容易先读全文再筛选 | 补全只读工具的 `path/value/goal/recall` 参数；技能明确区分有辨识度的搜索与泛词全文匹配，并禁止对已完整显示的材料重复准备 | 普通提示中真实调用 `jev_evidence`；原文回读、异常回退和同一工具调用内串联的回归通过 |

## 缓存证据

原生请求捕获中，六模型均得到：

- 实际档位序列：`high → high → medium → medium`。
- 顶部 `reasoning.effort` 始终为 `high`。
- 新档位通过追加 `configuration_update` 表达；此前 input 序列完整保留。
- `prompt_cache_key` 保持一致。合成端点的缓存 token 不代表真实命中率。

真实模型协议任务使用固定路由建议，特意不调用 Jev，以隔离传输机制。每个任务执行三次独立算术命令并提交结果，验收 `[323,667,1147]`；必须出现原生 high→medium 的 `applied` 回执才能通过。

| 模型 / 单次观察 | 顶部切档 | 追加配置切档 |
|---|---:|---:|
| GPT‑6 Sol：切档后第一步输入 token | 14,851 | 14,828 |
| GPT‑6 Sol：该步缓存 token | 0 | 14,464 |
| GPT‑6 Sol：整任务未缓存输入 | 22,228 | 7,305 |
| GPT‑6 Sol：整任务 GPT 总 token | 74,730 | 74,651 |
| GPT‑5.6 Sol：整任务未缓存输入 | 22,093 | 29,324 |
| GPT‑5.6 Sol：整任务 GPT 总 token | 72,400 | 71,830 |

GPT‑6 Sol 的未缓存输入观察值减少 67.14%，**并不是总 token 减少 67.14%，也不是实际额度减少 67.14%**。5.6 Sol 的追加组后来另一次生成缓存为 0，整任务未缓存输入反而增加；稳定前缀不保证每次命中，冷启动、服务路由和缓存失效仍存在。所有时间、总输入、缓存输入和输出分别保留在 [逐次 CSV](runs.csv) 与 [缓存原始记录](cache-runs.json)。

GPT‑6 Astra / Sol / Luna、GPT‑5.6 Sol / Terra / Luna 的真实追加配置任务均通过功能及改档验收。这里的 5.6 兼容结论只针对当前桌面原生后端实测，不能外推为所有公开 API 都支持。GPT‑6 Sol 的手动原生压缩完成，随后在不使用工具的情况下正确回忆三个结果。没有因此关闭压缩功能；自动触发阈值下的长会话完整性能尚未测量。

## 自然筛选：保留反例

输入是 180 条合成客服记录，要求找出重试导致、且尚未退还的多扣款记录。提示没有要求使用 Jev，没有强制全文读取。独立验收要求准确找出 8 个案例且原文不变。

| 首轮 | 裸 Codex | 候选筛选入口 |
|---|---:|---:|
| 验收 | 通过 | 通过 |
| GPT 总 token | 185,182 | 263,335 |
| 未缓存输入 | 24,101 | 29,241 |
| `prepare_output` | 0 | 1 |
| Jev API 调用 | 0 | 0 |

候选组总 token 增加 42.20%。已定位两个具体原因：

1. 泛词搜索先把大部分材料带进上下文，之后又准备同一文件，重复读取。随后增加技能约束，禁止这种调用顺序；后续单次验证另列，不能挑较好的一次替换本次结果。
2. 固定 30 行分块把独立记录混在一起；每块都含 `failed/pending` 等受保护词，18 块全部本地保留，根本没有进入 Jev 判断。因此 `no_exclusions` 返回完整原文。

**未放松错误、未解决事项、代码及结构化结果的保护，也未把原文保留功能删除来换取更漂亮的数字。** 记录边界分块与有限调用预算之间的取舍仍未解决；这类混杂材料暂时不能宣称能从筛选获益。技能约束也不能保证模型每次遵守。完整轨迹见 [自然任务记录](semantic-runs.json)。

### 后续发现：只读选择被通用工具审批拦截

增加“不要重复准备全文”的技能约束后，单次自然复测仍用了 276,128 GPT token（未缓存输入 23,259）。模型尝试 `jev_pilot select`，被宿主拒绝：`MCP tool call requires approval, but approval policy is never`。没有发出 Jev API 请求。这个结果同样保留，不能用后面的组件成功覆盖它。

已将 `select` 接到标记为只读的 `jev_evidence`，复用同一选择逻辑和完整回读。通用工具仍可执行原来的写入操作，权限要求没有降低。原生 code-mode 在 `approvalPolicy:never` 下实际完成只读筛选并把结果送入后续模型请求；修改/执行类操作仍不属于该入口。

随后对同样 180 条记录做真实 Jev 组件验证：按记录直接选择，6 次 `jev-1.13.0` 调用，4.119 秒；保留 64 条、排除 116 条、无延后，8 条目标证据无遗漏，原文回读完全一致。源文件 58,616 字节，返回 context 为 21,712 字节。详细 token 与事件见 [Jev 组件记录](jev-selection.json)。这是 62.96% 的正文体积下降，**不是 GPT token 或完整任务耗时下降**；没有付费 GPT 在该组件测试中消费这个真实 Jev 结果。修复审批后的普通任务是否稳定主动使用该入口仍待重复验证。

## 测试质量与消耗

- 本地 213 项测试通过；20 项既有原生合成端点测试、6 项缓存追加配置测试及 1 项只读候选筛选测试通过；另外六模型验证适配层默认开关路径。故障回退、人工设置优先、预算回基准、并行合并、原文回读、代码模式失败回退均保留。
- 初始协议预检的固定判断遗漏 `confidence`，被路由器正确拒绝，因此没有真正切档。这 4 个任务全部排除出有效比较，其中最后一项被中断后超时；消耗仍记账。探针已加入“必须真实切档”的验收条件，并阻止收到停止信号后继续下一任务。
- 预检进程的停止缺陷造成部分诊断短时重叠。本报告不从本轮耗时差得出加速结论，也不发布统计显著性。后续即便没有重叠的任务也只有单次观察。
- 本轮协议任务使用固定判断，不评估 Jev 判档准确率；自然任务发生的是工具调用，不等于 Jev API 调用。主对话后台开销不属于这些隔离测试。
- [消耗清单](accounting.json) 包含无效预检、失败和后续检查。原生独立压缩没有提供可对齐的新增输入/输出用量，记为未知，不能当作免费。订阅额度与实际扣费均未测量。

## 后续验收

本次可安装的是缓存传输修复、保守预算间隔、明确的文件筛选入口和无需写入审批的只读候选选择。本机已安装插件 `0.2.0+codex.20260924011258`；独立启动的进程链、安装指纹、两个 hook 和原生缓存开关均验证通过。当前桌面仍有旧版进程，需要正常重启后核对，不能用独立测试冒充已全面加载。见 [安装核验](deployment.json)。

下一轮性能结论应来自冻结策略后的重复、交错顺序、单并发真实任务，同时统计正确率、实际切档、缓存／未缓存输入、输出和 Jev 用量。记录分块问题解决前，不宣传通用筛选节省。
