# 为什么没有测出别人所说的 5–10 倍提升

2026-09-24，检查代码版本 `cba4c15b4f6c12a72f829816f0cf09d518eefd64` 及本机安装版本 `0.2.0+codex.20260924201153`。

**结论：先前的 2.14% 不是 Jev 相对 Codex 的整体加速率。我们比较了两种 Jev 实现，且产品还缺少当前 Chrome / Computer Use 的通用连续操作适配。路径判断也存在实际失败。当前问题主要在测量口径与集成设计，不能据此断言 Jev 只能带来几个百分点的收益，也不能保证补齐后一定达到别人的倍数。**

本轮是源码对照和小规模原因诊断；未修改、重装正在使用的产品，未重启浏览器或 Codex。

## 1. 对照组没有回答用户真正的问题

[此前 Chrome 测试](../browser-followup-20260924/chrome-recovered/README.zh-CN.md)两组分别是旧 Jev 逐候选分类、新 Jev 单个 Choice。每个正常任务两组都调用 Jev 六次，都把整个循环放在同一个工具执行单元里，没有一组是 GPT 实际逐步完成相同任务。

因此 2.14% 只描述已经使用 Jev 之后的实现差异。原报告的边界说明虽有写明，但拿这个小幅变化回答“插件整体是否大幅加速”，仍然没有完成用户要求的测量。预设正确路径脚本同样不能代替 Codex 对照：脚本已知道答案，省掉了规划和判断成本。

正确主比较应为：相同模型、档位、授权、工具、初始状态、目标和独立验收下，**普通 Codex 的实际执行**与 **Codex 规划 + Jev 连续操作 + Codex 验收**。普通 Codex 允许自然批量操作，不能为了做出倍数强行限制成每次只能点一下。两组都应计入规划、工具执行、失败、接管及验收，分开记录 GPT 原生用量与 Jev 用量。

## 2. 产品的主要加速路径尚未完整交付

代码事实：

- `src/pilot.mjs` / `src/server.mjs` 对外提供 `browser_step` 和 `browser_consume` 两个单步接口。
- `src/browser.mjs` 有通用 `runBrowserLoop`，但要求调用方提供 `observe / execute / verify`；仓库中的直接调用目前在单测内。
- 真正驱动官方 Chrome 和 Computer Use 的代码在 `scripts/acceptance/`，绑定本地事故测试页面、固定端口和验收结果，属于测试探针。
- 已安装 skill 把浏览器列为高级操作，参考文档说明可以批量循环，但缺少当前宿主可直接使用的通用 `createSession` 适配。现有后台自动化负责判档、输出筛选等，并不会把普通浏览器调用自动变成 Jev 连续操作。

这不代表单步接口不能用：agent 可以自行组装流程。但“具备库函数”与“普通用户安装一个插件后自然获得连续执行能力”有明显差距。临时测试脚本也不能充当通用适配交付。

有潜力产生倍数差距的机制，是将多次机械操作留在同一个受限工具循环中，减少 GPT 决策与上下文往返。若每步仍回到 GPT，由 GPT 再分别调 Jev、消费票据和执行，就可能在原有工作外增加调用，收益方向反了。我们尚无普通任务的成对原生轨迹证明实际消除了多少 GPT 轮次。

## 3. 查到的公开实现究竟做了什么

| 项目 | 核对到的代码或数据 | 对我们的启发与边界 |
|---|---|---|
| [wy-coliney/jev-browser-use](https://github.com/wy-coliney/jev-browser-use) | README 自述约 5–10 倍，限自身 EZCollegeApp 浏览器操作，排除服务端处理；[bridge.mjs](https://github.com/wy-coliney/jev-browser-use/blob/cf7e76607d4ec70592b24becadd0296dcda8177a/skills/jev-browser-use/bridge.mjs)提供连续 run/createSession、动作历史、进展检测和接管 | 减少主模型逐次参与是核心。沿用现有浏览器连接；我们应适配当前官方宿主，不能照抄其旧 API 名称。README 中的倍数是作者自述，未作为我们的测量结果 |
| [Sac-Y/Jev-cu](https://github.com/Sac-Y/Jev-cu/blob/main/scripts/loop.mjs) | 在宿主内循环，可由 planner 给当前 stepGoal，保留独立 verify，并构造候选和界面状态摘要 | 给 Jev 当前子目标，而非要求它每步自行拆解全部业务任务；摘要不能丢失区分候选所需事实 |
| [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast/blob/main/docs/performance.md) | 六次交替试验，同为 Jev 的两版运行时中位数 9.450→7.092 秒；浏览器协议调用中位数 1,092→101 | 同为 Jev 的比较也仅有约 25% 改善；通过批量读取和减少无效重判压缩工具开销。其独立浏览器实现不能直接替换用户要求的官方 Chrome / Computer Use 插件 |
| [ZJU-REAL/CUA-JEV](https://github.com/ZJU-REAL/CUA-JEV) | 区分 Jev Hybrid/GUI Only/Codex Hybrid；部分工作借结构化执行明显提速，但公开 Edge 为 79.5 vs Codex 77.4 秒，Excel 84.2 vs 39.2 秒 | 不是所有 Jev 任务都更快。预建任务适配器、执行通道差异与小样本必须披露，不能把用 API 替代 GUI 的收益全算成模型收益 |

研究仅阅读公开源码与文档，没有运行上游安装器或改动官方插件。当前 Agent Reach 检查为最新版本。

## 4. 子目标、历史与错误分支

当前 `browserStep` 发送 `goal / driver / observation`，未发送已执行动作的语义历史或当前子目标。宿主只积累步骤数和页面-动作指纹。在身份故障实测中，Jev 从密钥轮换问题走到部署记录 r42，后续仍预览会话恢复。最终验收拦截了错误，但中途已经多花操作和判断。

为定位输入表达问题，本轮安排八种组合：两个业务分叉 × 整段目标/当前子目标 × 两种候选顺序。观察来自合成重建，不是先前遗失的原始中间 AX；每组合仅一次，不能据此得出稳定准确率。

实际 **七次 Jev 请求**，输入 **3,657**、输出 **308 token**，响应模型 `jev-1.13.0`。第八种组合在 API 调用前被 `TASK_URGENT_RESERVE` 拦截，零费用，不能计为模型答错。按输入 $0.042/百万估算本次 Jev 费用 $0.000153594，未含 Codex 分析成本。

| 分叉 | 目标 | 候选顺序 | 结果 |
|---|---|---|---|
| 身份故障 | 整段任务 | 原顺序 | 正确；所选概率 0.65，confidence 0.47 |
| 身份故障 | 当前子目标 | 原顺序 | 正确；所选概率 0.88，confidence 0.82 |
| 身份故障 | 当前子目标 | 反转 | 正确；所选概率 0.77，confidence 0.66 |
| 身份故障 | 整段任务 | 反转 | **错误选择部署**；错误选项概率 0.59，confidence 0.39 |
| 结账故障 | 整段任务 | 原顺序 | 正确 |
| 结账故障 | 当前子目标 | 原顺序 | 正确 |
| 结账故障 | 当前子目标 | 反转 | 正确 |
| 结账故障 | 整段任务 | 反转 | **未请求：预算预留** |

四个子目标组合均正确，支持进一步验证分解任务；不能声称已修复。候选顺序改变伴随答案变化，尚不能分离位置敏感与模型随机波动。直接套用 confidence 0.55 会拦住这次错误，也会把 confidence 0.47 的正确答案交回 Codex，因此必须按成功完成任务的总成本校准，不能只看拦截数。

数据：[实际请求与响应](results.json)、[调用/拦截事件](events.json)、[计算与边界修正](analysis.json)。原脚本 scope 字段错误地写了八次实际调用，原件保留；以 calls=7 和七条 jev_call 为准。此缺陷不影响请求内容或上述计数。之后仅修正探针描述并补存 status/reason，没有重新发送请求；执行时脚本哈希见 analysis.json。样本不是完整浏览器任务或 GPT 性能比较。

## 5. 为什么只继续压 Jev 的耗时不够

重新汇总之前 Computer Use/Safari 结账用例的新策略两次运行：

| 部分 | 平均耗时 |
|---|---:|
| 任务总时间 | 5.783 秒 |
| Jev 决策阶段 | 1.840 秒，占 31.81% |
| 界面读取、执行与其他开销 | 3.943 秒，占 68.19% |

如果假设执行路径及其他时间完全不变，即使把这组 Jev 决策耗时降到零，速度也仅为原来的约 1.47 倍。这只是分段数据的算术上限，不是整体 Codex 相对 Jev 的加速上限。要获得更大的改善，必须减少主模型往返、无效操作和不必要的界面读取。

此外发现普通 MCP 路径每次 `browser_step` 都做网络环境维护，其中重复运行 Node 版本检测；之前合成测试直接调用库，未包括这段成本。本机五次只读检查为 13.9–17.2 毫秒。应从逐步决策路径移出或基于配置变更失效缓存，但这是小开销，不能用它解释几倍差距；本轮没有更改刚恢复的代理逻辑。

## 6. 具体整改顺序与验收条件

1. **补生产宿主会话适配**：一个插件内提供当前官方 Chrome、Computer Use 的可复用受限连续执行；由 agent 自行加载，用户照常讲话。保留当前标签页/应用连接和宿主权限，不启动第二套浏览器驱动。
2. **让 Codex 负责合理分解**：一次给出当前阶段目标、许可范围、需要保留的对象标识和验收条件；多步机械选择交给 Jev。规划及重新接管成本必须计入，不能用已知正确按钮序列伪装智能能力。
3. **补进展与对象一致性**：携带有界执行历史、阶段和已确认对象。目标对象矛盾、无有效进展或含混分支及时交回 Codex。禁止简单按按钮名称一刀切禁重复，避免破坏分页、展开等正常功能。
4. **降低真实工具开销**：把结果状态作为下一步观察；只在必要边界重新读取。仍保留目标新鲜度、授权范围及独立最终验收。加载等待先用确定性条件处理，不反复付费问模型。
5. **完整主比较**：普通 Codex vs Codex+Jev，同驱动同模型，允许两组自然批量操作，交替多次运行。记录总时间、成功率、主模型生成轮次、原生输入/缓存/输出用量、Jev 全用量、接管和失败成本；预设脚本只作工具延迟下限。

在这些条件完成前，不能把浏览器协作称为完整自动加速功能。正确方向是补齐真正替代主模型工作的路径，再按最终成功完成任务的时间与成本验证；继续在已有 Jev 循环内挤几个百分点，不能回答用户要的产品价值。
