# v15：功能回退修复与性能原因审查

日期：2026-09-23。审查基线：`40419bb2b589faf9ee1e497fd09a2f21af69dc32`（v14）。

**结论：上一轮优化确实存在功能回退，不能因为调用变少就视为优化成功。已撤回会漏判的停判规则，保留正常复用与硬预算。现有数据足以解释 token 增加的账目，但不足以把全部耗时增加归因到某一个组件。没有新的整体省时、省 token 结论。**

本次未主动新增付费模型测试。下面的性能数值全部重新计算自已有的 6 次真实任务；本次功能检查使用本地断言和真实 Codex 引擎连接合成模型端点。当前开发对话及其后台调用不计入这 6 次实验，也不是零成本。

## 1. 查出的功能回退及修复

| 问题 | 原行为为什么不合格 | v15 行为与验收 |
|---|---|---|
| 连续两轮未改档，跳过后续两轮 | 同一任务窗口的新请求也可能已经变简单，不能靠以前没改档推断新请求不需要判断 | 新请求重新具备判断资格；两轮未改档后，新请求仍可切 low |
| 一轮内两次维持基线就停判 | 后续阶段变化、失败、复用期结束都被拦住；恰好错过后半程降档机会 | 删除整轮停判，继续按复用期、事件和剩余预算判断 |
| 两次建议高于用户上限后停判 | 早期复杂不代表后期仍复杂，后续合法降档被挡住 | 始终遵守用户上限，但后续合法低档建议可以应用 |
| 未改档后遇到暂时网络故障，不再恢复 | 一次没有收益不能证明服务恢复后也没有收益 | 等待 15 秒后允许一次恢复尝试；持续失败不无限重试 |

先把 5 个功能需求反例放到旧 v14 上运行，得到 **4 失败、1 通过**。失败分别是：新任务未调用（4 次而非 5 次）、新阶段仍 medium 而非 low、失败未触发重评（2 次而非 3 次）、恢复时间为空。修改后 5 项全部通过。另补充了“两次被上限挡住，第三次合法降档”的检查。

此前有些测试断言的是“失败之后也只调用两次”，实际上是在认可功能退化。本轮改为验证“应重评时能重评，同时不突破上限”。保留的约束包括：用户档位上限、实时模型支持列表、4 次常规加 2 次保留调用、并行工具合并、重复回执去重、过期低档恢复、手动设置优先、网络故障降级，以及最低支持档位不做无可执行收益的判断。

真实原生协议检查新增序列：请求 1 为 high，请求 2 为 high，请求 3 为 medium，请求 4 为 medium；同时收到原生 `applied` 回执。证明连续两次不变后，实际请求参数仍能改变。这是合成推理端点的功能证明，**不是付费模型性能结果**。

修复可能比有缺陷的停判策略多花 Jev 调用。恢复必要能力优先于让调用计数好看；不能把这次修复宣传成已经省钱。

## 3. 为什么 GPT token 增加：可精确复算的四部分

每次模型生成都重复携带当时上下文。缓存输入仍属于 input/total token；缓存影响计费及潜在延迟，不会让上下文在总 token 中消失。

设生成次数为 n，首个输入为 I，后续输入相对首个输入的增量和为 H，输出合计为 O，则总 token = n×I + H + O。以下是严格相加的**账目分解，不是随机实验得到的因果贡献**。

| 自动组减裸运行 | 修复 Promise 缺陷 | 排查连接池事故 | 合计 |
|---|---:|---:|---:|
| 多一轮生成再次携带的基线输入 | +14,761 | +14,819 | +29,580 |
| 首轮输入差异在各轮重复 | +6,503 | +5,448 | +11,951 |
| 后续历史增长量差异 | +5,366 | −29,053 | −23,687 |
| 输出差异 | +485 | +850 | +1,335 |
| **总差异** | **+27,115** | **−7,936** | **+19,179** |

具体观察：

1. **额外生成带来的上下文重放是很大的成本。** 修复任务 6→7 次，事故任务 5→6 次；不是只多生成一句短答案的成本。
2. **插件发现与使用说明也占上下文。** 自动组首个输入分别多 929、908 token，后续会继续携带。该差异与安装插件相关，但也包含其他首轮上下文差异，不能把每个 token 都严格归给 SKILL 正文。事故自动组实际发生了一次读取 SKILL 的命令；它不是零成本。
3. **工作路径改变可能省输入、也可能增加步骤。** 事故裸运行直接读全日志；自动组先看头尾，再精确搜索，少携带许多日志文本，历史增长少 29,053 token，但多了检查/读取步骤。事故的 GPT 总 token 实际减少 7,936；修复任务增加 27,115，抵消了这部分收益。不能说所有任务都更多，也不能把精确搜索带来的收益说成 Jev 筛选收益。
4. **Jev 没有替代 GPT 工作。** 4 次 Jev 均用于判档，没有实际切档，也没有语义操作或输出筛选应用。因此额外产生判断开销，却没有该实验中可观察的委派收益。14 个功能存在，不等于每个任务都应调用 14 项。

复算结果：[accounting.json](accounting.json)、[逐任务 CSV](runs-accounting.csv)、[分解 CSV](token-decomposition.csv)。脚本：[causal-audit.py](../../../scripts/acceptance/causal-audit.py)，对每项累计用量、逐次用量和分解之和执行断言。

## 4. 缓存：增加了未缓存输入，不能重复计算为总 token 增量

自动组 GPT 输入比裸运行多 17,844，缓存输入反而少 6,272，所以未缓存输入净增加 **17,844 − (−6,272) = 24,116**。

修复任务自动组第一次、第三次生成的缓存输入都是 0；裸运行第一次已缓存 8,320，后续也有较高缓存覆盖。这说明两组缓存状态不等价。它可能影响实际成本和时间，但没有服务端遥测，无法证明具体是哪一个缓存机制导致失配。

已有原生协议探针证明初始输入前缀序列化内容保持不变，不能据此保证服务端缓存命中。此次 0 次切档，所以“切档破坏缓存”不能解释这组结果。推理 token 是输出的子集，报告不再另加一次。

## 5. 为什么时间增加：已测到什么，缺少什么

| 可观察项目 | 修复任务 | 事故任务 | 合计 |
|---|---:|---:|---:|
| 自动组较裸运行更慢 | 12.863 秒 | 14.757 秒 | 27.620 秒 |
| Jev 请求累计时间 | 1.759 秒 | 1.550 秒 | 3.309 秒 |
| 路由 decision 累计时间 | 1.812 秒 | 1.602 秒 | 3.414 秒 |

Jev 判档包括首步等待及工具边界的同步等待，确有新增延迟。decision 比请求本身多出的时间包括工具合并等待和本地处理等；代码默认合并窗口是 50 毫秒。钩子还会启动本地 Node 进程、通过 socket 通信。自动大输出处理与路由按顺序执行，但这 6 次任务没有应用输出筛选，不能将其筛选耗时拿来解释本次慢速。

**3.309 秒不是 27.620 秒的完整解释。** 额外 GPT 生成、不同工具路径、更长输出、缓存差异，以及服务端/网络波动都可能贡献剩余时间。旧原生记录中所有命令 `durationMs` 都是 0，未保存逐次生成和工具事件时间戳，所以无法把剩余时间精确切成“GPT 推理多少秒、工具多少秒、网络多少秒”。零不是工具免费或瞬时完成的证明。

路由累计时间还可能与其他并行工具重叠，不能简单从墙钟时间减去 3.414 秒，声称余数全是 GPT 推理。空载组不调用 Jev，修复任务仍用了 134.379 秒、9 次生成；这进一步说明一次运行的路径和时延波动很大，不能把差值全部归给网络或 Jev。

本轮为后续 runner 补充单调时钟记录：turn/start 发出/回执、工具开始/完成、hook 开始/完成、token 用量和任务结束事件，仅存类型/标识/时间，不存消息、命令或错误正文。该记录能区分宿主可观察区段，仍不等同于提供方内部推理时间。旧结果不补造时间戳。

## 7. 尚不能下结论及下一轮的验收原则

- 这次修复证实恢复了应有重评能力，尚未重新测得 v15 的整体性能收益。没有以“关掉功能”的方式宣布节省。
- 路由内容只看到任务、公开进展和有限工具证据，无法保证下一步判断最优；不能为追求改档次数强制降档。
- 非零 shell 退出码可能是正常差异/无匹配。例如修复任务的 `git diff --no-index` 返回 1。当前保守失败信号会倾向复查；本轮没有简单忽略退出码，以免漏掉串联命令中的真实错误。这是后续精确事件分类的候选问题，**没有证据证明它造成了本次新增 Jev 调用**。
- 同步钩子和说明加载有固定成本，轻量任务未必能摊平。大型、未解决的语义候选任务才可能提供足够替代空间；几百个相关仓库存在不能证明本接入在任意任务都省时省额度。
- 下一次性能对照必须保留相同质量门槛、明确缓存状态、记录各步时间、固定主比较基线、平衡顺序并重复；同时计算 GPT、Jev 和重试成本。不会通过多次试到一个正数才发布。
