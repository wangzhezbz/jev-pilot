# Chrome / Computer Use 完整任务验证与优化

2026-09-24。本轮不是上一轮“操作片段快 72.61% / 28.65%”的重复宣传。我们把任务内规划、页面导航、接管恢复和最终原生验收纳入计时，查看收益是否还能保留。

**结论：8 次任务最终验收全部通过，4 对中两对更快、两对更慢。GPT 总 token 合计减少 43.96%，但包含大量缓存输入；GPT 输出反而增加 16.67%。本组完整任务合计慢 25.43%，不能据此承诺稳定加速或实际账单节省。**

## 为什么循环快，完整任务却未必快

1. **临时规划成本不可忽略。** 原有入口需要生成目标、阶段完成回调、身份约束、最终校验和控制项列表。正常自动组的执行循环约 4.74s / 9.92s，整个任务却是 31.11s / 36.69s。差值还包含规划生成、工具往返、导航和验收，不能全部归咎于 Jev API。
2. **接管会重新引入 GPT 等待。** Chrome 报表的 Analytics 入口含义不够明确，概率 0.58 时保守退出。原生选中入口后 Jev 完成后五步。没有降低概率门槛，也没有重复付费猜同一状态。
3. **宿主脚本也会出错。** 首次报表合同引用了当前 REPL 单元不可见的变量；修正费用和时间保留在这一组里。它是本次接入代码生成问题，不是 Jev API 变慢。不能把修复过程从成绩里删除。
4. **长任务共用预算有真实代价。** 本轮开始时当前任务窗口已用 6 次、约 2.38s。默认每小时等待额度 20s，其中 4s 留给紧急请求。最后一个自动任务剩余普通额度不足 1s，最后一步未发起收费请求，交回原生完成。没有更换 taskId、重置预算或放宽额度。
5. **Computer Use 观察也有波动。** 报表自动循环的观察阶段约 3.24s；文档约 7.69s。相同接口并不意味着每次宿主响应时间相同。
6. **较少轮次不等于较少输出。** 自动化准备代码比单次点击长，导致本组 GPT 输出增加 487 token。巨大的总 token 降幅主要来自少次重复读取长对话缓存，不能按未缓存输入价格计费。

## 本轮落实的优化

- **精简默认回执，完整结果仍留在宿主。** 新增 `summarizeHostResult`，保留状态、失败原因、真实用量、执行不确定性和独立验收要求。成功时不重复向 GPT 展示整页及完整轨迹；接管时保留有界页面片段与近期步骤，截断有明确标记。实测三份成功回执从 2,723–3,019 字符缩至 630–632 字符，减少约 77–79%。这是字符量变化，不是单独测出的 token/耗时节省。
- **识别真实链接名称。** `Value`、`ID`、`Help` 等辅助字段不再阻止准确名称匹配；同名不同链接仍视为歧义，不自动任选。完整元数据仍参加拒绝/风险判断和新鲜度校验。本轮两类宿主均实际通过链接导航。
- **收紧“Preview”例外。** 带预览前缀的删除/提交动作不能借前缀绕过限制；保留严格的只读回滚预览名称。旧版正确预览和危险标签均有回归覆盖。
- **增加简短任务定义 `defineTask`。** 常见只读导航用目标、阶段、可见证据字符串表达，插件生成通用回调；复杂情况保留原回调 API。空证据、错误身份、最终证明与禁止状态冲突均有验证。该项在八次实测后加入，已通过离线回归及四份真实最终页面回放；**没有把它宣传成已实测的新增速度收益**。

自动组实测已经使用精简回执和链接修复；最后新增的简短定义入口不会追溯改变表中结果。预算、低置信度交接、状态复核、一次性动作票据和最终原生验收均保留。

## 实验范围与原始数据

- 两个新的合成业务任务：指定区域/季度/批准版本的报表预览，指定发布状态/语言/版本的运维文档预览。均为六步，含相似干扰项和禁止写操作。
- 四对、八次，按 Chrome 报表原生→自动、Chrome 文档自动→原生、CUA 报表自动→原生、CUA 文档原生→自动交替顺序。每对只有一次，没有统计显著性或广泛稳定性结论。
- 测试者编写了页面与验收规则；属于非盲合成任务。未把有序点击答案传给 Jev。CUA 在 Chrome 后执行同一业务任务，因此存在熟悉任务的影响。
- 计时从已准备好的普通宿主中开始导航，到独立最终复读及答案形成。包括任务内规划、错误恢复、接管；不含插件安装、测试页编写、宿主初始化、研究/报告撰写。启动工具调用的 GPT 生成时间在时钟起点外，但其 token 纳入用量。不是从用户点击“发送”到最终报告展示的全会话耗时。
- 每次原生动作先根据官方界面观察选取控件，再读新状态。未给原生组强加额外思考或睡眠；未把硬编码点击脚本当作 GPT 基线。这里的原生 UI 组表示不委托浏览器步骤，并非卸载整个 JevPilot 的对照组。
- 第一次原生预检中浏览器自动翻译使最终精确文本校验失败，保留 `translation-precheck` 原始记录。随后仅给合成页面加 `translate=no`，未改浏览器设置，在首次收费 Jev 请求之前固定页面并重新开始八次对照。预检不算产品成功率/配对成绩。

## 成本怎么算

没有获得本账户的逐任务扣费账单，本报告不声称已节省某个金额或订阅额度。按每百万 token 的实际价格，令 `Gi/Gc/Go` 为 GPT 普通输入/缓存输入/输出单价，`Ji/Jo` 为 Jev 输入/输出单价，则本组估算净节省为：

`(3309×Gi + 1142784×Gc − 487×Go − 19631×Ji − 1093×Jo) / 1000000`

需要用用户实际计费方式代入。若订阅额度不按该 API 定价扣减，就不能用此公式推算订阅节省。
