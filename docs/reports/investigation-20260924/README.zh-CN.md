# 一次调用检索候选版：实现、失败记录与性能验收

日期：2026-09-24。结论：**未达到“加速且省 token/额度”的发布目标，不替换已安装的桌面版本。** 本报告保留全部开发阶段，不以最后一次结果覆盖失败样本。

后续：[连接复用修复与逐步缓存归因](../connection-fix-20260924/README.zh-CN.md)已发布。它补上了真实证据保留验收，并纠正了缓存原因的归因；本页原始任务数据及未达标结论保持不变。

## 最重要的结果

最后一组为同一策略文档任务、两次配对、AB/BA 顺序，四次均通过功能验收。原生 GPT-6 Astra 固定 high；候选组启用调查工具、条件提示和重复长行的无损显示。没有自动切档或切模型。

| 两次任务合计 | 原生组 | 候选组 | 变化 |
|---|---:|---:|---:|
| 任务耗时 | 172.35 秒 | 199.47 秒 | **+15.74%** |
| GPT 总 token | 199,031 | 159,693 | −19.76% |
| 输入 token | 197,265 | 157,774 | −20.02% |
| 缓存输入 token | 157,696 | 110,080 | −30.19% |
| 未缓存输入 token | 39,569 | 47,694 | **+20.53%** |

第一对时间 −5.84%、token −22.91%；第二对时间 +44.24%、token −16.48%。方向不一致，样本不足，不能声称稳定加速。总 token 的下降主要伴随缓存输入减少；未缓存输入和输出均增加，**不能据此声称省费用或 ChatGPT 账户额度**。未对不同类型 token 假定同一价格，也未将不同模型的 token 当成可直接比较的费用。

## 本轮做了什么

1. 新增只读 `investigate`：一次调用完成字面查询、相邻证据窗口合并、来源定位和必要筛选。限制搜索范围与读取量；返回限制、跳过数量和完整覆盖状态。原文快照可恢复；恢复范围仅为已经保存的窗口。
2. 增加条件提示：只有工作区存在足够多文本材料、任务确实涉及调查、原生运行时确认工具可用时，提示优先使用。普通小任务、逐字读取和工具不可用时绕过。它是指导，不保证模型采用。
3. 对 Markdown/纯文本/日志中的重复长行做无损字典显示：保留原文和每次出现位置；代码文件、保留标记冲突、收益不足和 exact 模式不折叠。这里的“压缩”不是语义摘要。
4. 调查专用的 Jev 请求让每道问题携带自己的候选，避免每题携带整个候选池；其他操作保持原请求形状。官方接口允许问题拥有独立 instructions，且返回 usage：[TypeSafe API](https://docs.typesafe.ai/api)。本轮未取得旧/新请求都成功的配对，因此没有声称这项实测省了多少 Jev token。
5. 修复显示预算顺序：之前不确定证据先占预算，会把已确定相关的来源推迟，迫使再次读取。成功完成语义筛选后保留所有未排除窗口，超过建议显示预算时明确标记。
6. 增加真实接口阶段计时和完整开发审计。诊断只记录 DNS/TCP/TLS/首字节/总耗时与状态码，不记录凭据、请求体或代理详情。

没有改已安装插件、现有桌面路由策略、主模型、VPN 或代理配置，也没有因本轮测试要求用户重启。

## 为什么上一版会更慢、更费

| 已观察到的问题 | 证据 | 本轮处理与剩余限制 |
|---|---|---|
| 提供工具不等于模型会用 | 第一阶段文档任务均未调用 investigate | 加条件提示；后续确实采用，但新增提示本身也有上下文成本 |
| 重复背景占满预算，触发再次读取 | 第二阶段调用 investigate 后仍 recall/原生补读 | 无损重复行显示；最后两次候选任务均一次 investigate、零 recall |
| 不确定证据挤走明确相关来源 | 成功的真实 Jev 分类仍把三份必要材料放进 deferred | 修复成功筛选后的保留策略；离线回归通过，修复后真实验证遇到连接超时，未完成在线验收 |
| 等待 Jev 可能成为纯额外开销 | 8 次语义 API 尝试中 7 次超时、1 次成功 | 保留有限截止及本地降级；没有延长全局连接截止。不能假设每次调用净赚时间 |
| 总 token 与缓存收益不一致 | 最后 A/B 未缓存输入 +20.53% | 报告分开计量。尚未证明是哪一段提示/缓存前缀造成变化，不把相关性当因果 |
| 轮数下降仍未转化为时间下降 | 10→8 次生成，但 172.35→199.47 秒 | 当前事件计时不足以精确拆分模型执行、服务端等待和网络等待，原因尚未完全定位 |

不能把最后一项直接归咎于 Jev：这四次完整任务根本没有付费 Jev 调用。也不能归咎于 VPN 或模型“想太多”：现有证据不足以区分这些原因。

## 全部真实 Jev / 网络检查

语义组件测试用来源标签打破重复行，以确保实际进入 Jev 分支。它是专门的组件用例，不是自然任务采用率或加速证据。

| 尝试 | 请求数 | 结果 |
|---|---:|---|
| 原共享候选池 | 2 | 约 1.8 秒截止，两次超时 |
| 第一次原子请求改动 | 2 | flag 放错分支，实际仍是旧 profile，两次超时；保留为失败开发记录 |
| 修正 profile | 1 | 每题独立候选已生效，约 1.8 秒超时 |
| 总截止上限提高到 5 秒 | 1 | 仍在约 2 秒截止，连接截止另有限制 |
| 增加阶段计时 | 1 | 成功：765 ms，jev-1.13.0，输入 11,498 / 输出 437；发现必要来源被预算推迟，质量未过 |
| 修复保留策略后 | 1 | 约 2 秒超时；TCP 已建立，TLS/首字节未完成，HTTP 状态 0；本地降级，部分必要来源仍需 recall，组件未过 |

8 次语义尝试：1 次响应成功、7 次失败且 usage 未知。另有一次小型颜色判断诊断成功：jev-1.13.0，输入 315 / 输出 31，约 586 ms。全部已知 Jev 用量为输入 **11,813**、输出 **468**，另有 **7 次未知用量**；未知不是零。它们是本轮开发验证成本，独立列账，没有混入最后四次完整任务的零 Jev 调用统计。

不带认证、不会调用模型的 API/docs 探针能连接。最后失败请求的 DNS≈0.00007 秒、TCP≈0.00025 秒、TLS=0、首字节=0、总时长≈2.002 秒；这能定位该次失败发生在连接建立阶段，不能说明所有历史超时都相同，也不能确定是代理、上游还是其他网络因素。未更改网络配置。

## 验证与边界

- 最终本地自动测试 **253/253** 通过，包括调查、恢复、隐私路径、预算、失败回退、真实 MCP 进程调用和请求 profile 隔离。
- 原版 Codex 运行时合成端点验收 **27/27** 通过，覆盖 Astra/Sol/Luna、5.6 Sol/Terra/Luna、档位、缓存前缀、人工选择、失败与工具边界；合成端点不是付费模型性能测试。
- 独立原版运行时检查确认 UserPromptSubmit 提示进入实际模型请求，并核对工具可用；不是本次桌面已加载候选版的证据。
- 付费完整任务固定 GPT-6 Astra/high、单任务并发，来自 app-server 原生后端，不是桌面 UI 延迟。最后两个配对按 AB/BA 顺序执行，未做统计显著性声明。
- 第一条 packed 原生样本与两次短的失败 Jev 组件请求约重叠 1.83 秒。保留这一方法缺陷，不据此作因果时间声明。
- 工具事件通知的起止间隔出现不合理的亚毫秒值，可能经过缓冲/合并；公开字段 observedToolIntervalUnionMs 仅为宿主通知区间，**不可从总时间扣除后冒充模型耗时**。
- 逐题 profile、5 秒证据总截止、更窄的提示适用范围和语义结果保留修复晚于 packed A/B。它们有各自回归/组件记录，最终修订没有新的完整任务 A/B。为避免冒用结果，保留了当时 14 个实际被测文件的源码快照与协议哈希。
- 各阶段是开发前后版本，不混成统一随机试验，不用第一阶段偶然较快但未采用工具的结果宣传收益。

## 交付与下一步门槛

候选代码和完整报告保存在开发分支，尚未作为默认版本安装。该方案证明可以减少重复阅读和部分输入量；**尚不能作为“加速省额度”的产品成果发布**。
