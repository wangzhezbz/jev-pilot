# 固定主模型的语义委派对照

日期：2026-09-24。**4/4 次任务通过验收；计入 Jev 的已知总 token 少 9.74%，端到端时间多 12.60%，未缓存 GPT 输入多 43.77%。没有同时证明省时与节省费用。**

## 试验边界

48 条新编写的产品需求，区分真正需要“断网创作/修改、联网后同步”的场景、只读缓存/联网工作流/永久本地工作流，以及条件不明确的场景。两次全文、两次 Jev 预选，顺序全文→预选→预选→全文，单并发。

主模型始终是 GPT-6 Astra、固定 high，原生启动回执确认该模型，没有档位路由和其他 MCP。使用现有 Jev select/recall 实现进行预处理，两组 GPT 指令相同；预选正文与全文使用相同记录格式。完整原文对两组都可用。

**这是委派机制试验，不是普通桌面对话自动触发验收。** Jev 在 GPT 开始前由测试程序调用，普通会话中的工具选择/调用开销不在这个组件入口里。不得将其结果宣传为当前插件日常使用收益。

预处理如漏掉任何必选或需复核记录，或无法完整回读，会直接停止并保留失败；本次两次都通过，没有重试挑选。GPT 的最终 include/review 集合、报告 ID 和源文件保持使用独立固定验收。报告理由仅检查存在及 ID，未对任意文字解释做完整语义质量证明。

## 真正发生了什么

原始证据正文 10,345 字节，Jev 分别保留 7,454、7,208 字节（34、33 条记录）。所需记录和需复核记录没有丢失，原文回读一致；但筛选比例有限，保守阈值没有为了测试而降低。

两次预选任务随后都执行了 `cat source-archive.md` 读取完整原文。全文对照也会读取两份输入，四次轨迹均保留。这个组件入口只提供了选出的正文和原文位置，没有向 GPT 提供生产工具的完整筛选元数据；因此不能把这里的全部回读直接归因于生产插件实现错误。它暴露了一个待验证的接口问题：如何让主模型理解覆盖范围、保留不确定项并按缺口回读，而不是重做全文检查。

全文两次的生成次数为 5、7；预选两次均为 5。总体 token 下降与第二次全文多两轮生成有关，不是一个可以单独归因于删掉证据的因果估计。主模型自行检查原文可能有质量价值，不能直接禁止回读来制造收益。
