## 3. 反例具体发生在哪里

### 文档筛选的费用

原生组未缓存输入 **13,383**，自动组 **45,714**。自动组前两次请求分别有 16,184、17,000 输入 token，缓存命中均为零；对应原生组已有 8,832、14,976 缓存 token。这是估算费用翻倍的主要可见组成部分，不能仅由 GPT 总 token 多 8.22% 解释。

两组都是 4 次 GPT 生成。自动组确实使用 `jev_evidence.prepare` 的无损来源表示，保留 90 条记录，没有语义剔除；但本例第三次请求输入仍从原生的 20,401 增至自动组的 22,249。插件工具定义、调用参数、来源标记等开销并未被这份中等长度文档的压缩收益抵消。**存在压缩功能，不等于整次 GPT 请求一定更小。**

### 文档筛选的时间

自动组首条公开消息的 started→completed 观测窗口为 **53.659 秒**，原生为 **1.123 秒**，差约 52.536 秒；整项任务差 52.437 秒。该窗口解释了本次绝大部分观测延迟，但不能从公开事件判断是服务端排队、流传输、网络抖动还是其他生成等待。

三次 Jev 判断的 API 耗时合计约 **1.332 秒**，工具准备调用约 **0.009 秒**。不能把 52 秒延迟直接归因于 Jev 推理，也不能删掉这次慢运行后宣布稳定加速。缓存未命中的服务端原因同样尚未被证明。

### Computer Use 的接手

这次新测试的 `scope` 回调要求页脚是独立的中文 `文本` 节点。Safari 最终 AX 把正文和页脚合并成一个英文 `text` 节点，范围匹配失败，导航器正确停止并报告 `HOST_DRIVER_ERROR`。GPT 重新读取后核验结果，没有重复点击。

这属于**本轮测试/接入范围提取过严**，不是 Jev 选错按钮，也不是网络故障。它真实地增加了一次接手，已计入结果。不能因此宣称 v19 在所有应用上的 Computer Use 已完全验收。

## 4. 当前可下的结论与后续工作

1. 可以确认：本轮有真实改档、真实 Jev 界面动作、独立结果核验；功能并非只做了建议。
2. 多步低风险 AX 导航减少 GPT 往返，在这两个样本中减少了 GPT token 与估算成本。Computer Use 的接手会明显吞掉速度收益。
3. 普通代码/文档的整体收益尚不稳定。本轮三项更快且更便宜，一项明显变差；包含全部样本的总费用、总耗时仍略升。
4. 下一轮应单独修正范围提取，使其按已验证页面子树边界工作，并覆盖文本节点合并和本地化；避免依赖页脚必须单独成行。修复后的结果应另列，不能替换本轮。
5. 文档准备应按包含来源标记、调用参数及工具说明的净收益做准入；保留完整召回与显式调用能力。再用同条件的重复对照观察缓存复用和生成等待，不能为了省钱关闭应有功能或抹去负样本。

每个新用例只有一对，本轮不能提供可信的稳定收益区间。本轮只测 Astra；没有新增 Sol/Luna/5.6 性能证据。macOS 两种界面真实执行不等于 Windows/Linux 桌面实操验收。

长上下文触顶压缩、远程页面输入/滚动/视觉操作、故障重试、多轮任务恢复以及全部 14 项功能的生产收益，**不在这次少量任务的完整覆盖范围内**。既有回归测试通过，也不能替代这些实操证据。
