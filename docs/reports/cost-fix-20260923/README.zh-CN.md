# JevPilot 成本回归排查与 v11 修复

本轮由 v10 的负收益实测触发。历史报告和原始结果保留在 [v10 验收报告](../validation-20260923/README.zh-CN.md)，不以修复后的结果覆盖历史失败。

## 为什么越用越慢、消耗越大

### 1. 自动判档缺少用户成本上限

v10 在 21 对双方通过验收的任务中耗时增加 27.57%，GPT 总 token 增加 14.61%。整组 48 次尝试中有 20 次真实切档，全部为 medium → high，没有降档。GPT 推理输出在匹配样本中增加 147.16%。

代码直接应用受支持的 Jev 建议，没有将用户原始档位作为上限。复杂任务描述又贯穿后续判档；晚期预算规则阻止降低当前强度，恢复规则只向上恢复，无法纠正已经自动抬高的档位。这套规则支持“自动改档”，却没有实现用户期待的“以降低成本为目标”。

这些是源码和回执证实的行为。没有单独进行因子实验，因此不能把全部耗时差精确分摊给升档、网络和重读。

### 2. 自动过滤误用了有长度预算的证据选择器

v10 自动过滤调用 `filterOutput(... budget:10000)`。这个函数既能排除无关内容，也能将仍然相关、但超出预算的内容暂存为 deferred。自动替换只检查输出长度缩短，没有检查缩短的原因。

旧对照中 13 次实际替换，语义排除数全部为 0，累计 85 个 deferred 块。249,665 字节的输出缩减仅是局部截留，不是节省 GPT token 的证据。任务仍需要这些内容时，模型必须再读取；上下文中还会多出过滤说明和重复片段。

### 3. Jev 本身不是免费、零延迟

旧对照包含 105 次真实 Jev 请求，14 次失败；已知输入 258,612 token、输出 11,305 token，累计调用等待 107.025 秒。等待时间可能与其他工作重叠，不能直接等同整项任务多出的墙钟时间。

按 [TypeSafe 官方输入价格](https://typesafe.ai/) 每十亿输入 token 42 美元，已知输入估算约 $0.010862；输出费用、失败请求未知用量和 Codex 账户扣费不在此估算内。便宜的附加判断仍然是附加成本；只有实际替代了更多主模型工作，才可能得到净收益。

指标中另有漏项：`missingUsage` 原来只统计成功但缺输入用量的请求，失败且没有返回用量的请求没有算进去。未知不等于零。

## 已实施的修复

- **用户档位作为上限**：自动路由可降档，遇到复杂步骤可恢复到用户档位；不能自行升到更高档。手动调整仍更新上限，模型选择不变。
- **无效越界建议停止**：连续两次建议超过上限，就保持用户档位并停止本轮后续判档；新用户输入或手动设置可以重新评估。这可能放弃后续降档机会，目的是限制已知无执行收益的调用。
- **迟到的回调可以回归上限**：调用预算接近耗尽时，仍允许旧的高档回到用户档位，只阻止开启新的低于基线且无法持续复查的降档。
- **自动过滤不得暂扣相关内容**：保留全部未被排除的证据；存在 deferred 就不替换；没有语义排除或精确去重也不替换。手动、显式的预算检索不受此改动影响。
- **重读放行**：同一轮再次读取已经过滤过的同源内容，返回完整原文，不再让 Jev 过滤。无收益冷却按内容哈希隔离，变化后的内容仍可重新检查。
- **用量缺失完整计数**：失败或成功请求中，只要输入或输出未知，就标记未知用量；已知 token 求和不会伪装成完整账单。

## 验证范围

本机单元及回归测试 **170/170 通过**；原版引擎配合合成模型端点的接口验证 **15/15 通过**，见 [原生验证回执](native.json)。这些数字验证边界行为，不是性能成绩。

新增回归覆盖 medium 上限、手动设置优先、晚期回归、停止无效判档、540 行全部相关日志完整保留、同源重读、内容变化及失败调用的未知用量。

真实对照采用 GPT-6 Sol、Luna × 并发错误修复、540 行事故日志分析 × 固定 medium、v11 自动，共 8 次尝试。任务和独立验收器复用旧实验，两组顺序交替，每项只有一次重复。代码在实验开始前冻结，不根据中途结果修改策略。

这是小规模修复探测，不能证明普遍收益。原生接口合成验证、报告编写与部分模型任务有时间重叠，机器没有独占，秒级速度差尤其需要保守解释。测试经真实原生引擎和桥接层运行，不是桌面 UI 延迟或订阅额度扣费测量。

## 本轮真实结果

8/8 尝试完成，8/8 通过原先冻结的独立验收；4 对完整对照均纳入。没有替换失败样本。主模型任务没有失败，Jev 请求有 3 次失败。

| 指标（4 对汇总） | 固定 medium | v11 自动 | 自动组变化 |
|---|---:|---:|---:|
| 总耗时 | 304.299 秒 | 230.053 秒 | −24.40% |
| GPT 总 token | 833,013 | 661,283 | −20.62% |
| 未缓存输入 token | 126,624 | 119,022 | −6.00% |
| 输出 token | 8,533 | 6,709 | −21.38% |
| 推理输出 token（包含在输出内） | 2,294 | 1,319 | −42.50% |

| 配对任务 | 固定耗时 | 自动耗时 | 固定 GPT token | 自动 GPT token |
|---|---:|---:|---:|---:|
| Sol 并发修复 | 72.642 秒 | 86.015 秒 | 118,675 | 220,351 |
| Luna 并发修复 | 154.226 秒 | 46.920 秒 | 232,815 | 94,357 |
| Sol 日志分析 | 39.482 秒 | 32.263 秒 | 212,768 | 170,110 |
| Luna 日志分析 | 37.949 秒 | 64.855 秒 | 268,755 | 176,465 |

**这些正的汇总差值不是已证实的 Jev 收益：实际切档 0 次，实际输出过滤 0 次，所有任务保持 medium。** 6 次高于用户档位的建议被挡住，相关内容 deferred 为 0。4 对中 2 对更快、2 对更慢。平均耗时尤其受 Luna 并发修复这一对影响。

自动组另付出 **17 次 Jev 调用**，其中 3 次失败、3 次用量未知；已知输入 **35,666**、输出 **1,710**，累计 API 等待 **14.360 秒**。已知输入费用估算 **$0.001498**，未含未知请求和输出费用，不能当作最终账单。GPT 与 Jev 是不同供应方的 token，不能简单相加当作统一费用或订阅额度。

例如 Sol 并发修复，自动组总 token 多 85.68%，但未缓存输入仅多约 1.84%；原生用量快照从 6 次增加到 11 次。大量差异来自更多模型生成及重复的缓存上下文。这个差别不能全部归因于 Jev，而是说明单次任务的模型执行路径、缓存和响应等待会严重影响结果。未做因子分解或足量重复，不宣称各项占比。

对四份事故报告还进行了额外的 Codex 文本复核：自动组两份保留了结算影响未知和观察窗口范围；一份固定组把“零 503”写成“error rate fell to zero”，措辞超出了严格原始观察。这是额外的定性复核，未改变预注册通过标准，也不是独立人工审计。

## 当前结论与安装状态

源码修复、170 项回归、15 项原生接口验证与本轮 8 次真实任务均已完成。可以确认不再擅自越过用户档位，以及自动过滤不会为了长度预算扣留仍相关的证据。

**仍然没有验证“默认开启后稳定省 token、加速或节省账户额度”。** 本轮付费判档没有转化成实际降档，过滤判断也没有产生可用替代结果；它们仍是附加工作。这一事实不会因为汇总平均值变好而消失。后续效率改进必须证明减少了主模型工作，并通过质量相同的对照，而不是继续以调用成功、字节缩减或偶然快的一次任务代替收益。

安装回执见 [installation.json](installation.json)：修复版已经写入本机适配层和插件缓存，哈希匹配，下一次桌面启动会加载。当前两个仍存活的桥接进程加载 v10，`loadedRevisionMatches=false`；没有强制中断现有任务，也不声称当前桌面已经切到 v11。

本次排查会话自身也出现了旧版 medium → high 的真实首步转发及后续 5 次 high 建议，见 [普通会话回执](ordinary-v10-regression.json)。这证明问题存在于实际桌面链路；修复并非仅改测试脚本。
