# JevPilot 深层成本审计：不止是升档与截留

2026-09-23。审计基线为 `84fcd49cfcffb6fa778c9864a381436e96a9ca3d`。本轮复用之前的真实模型记录，新增复现使用本地合成输入和注入的确定性假判断，**这些复现脚本的收费 API 调用为 0**，不包含正常桌面会话自身的后台自动判档用量。本地字节与 CPU 测量不等同主模型 token、端到端加速或账户扣费。

**此前排查范围过窄。当前产品的主要缺口，是把可调用的辅助模块当成了已实现净收益的工作流：Jev 作出判断以后，Codex 经常仍需完成原本的阅读、推理和验证。** 两次串联不自动等于替代。

## 新确认的缺口

| 问题 | 证据与影响 | 状态 |
|---|---|---|
| 1. 没有按模块验证净收益的启用条件 | 现有 guard 限调用数、字节和等待，但没有证明被省去的主模型工作足以覆盖额外判断。v11 的 17 次真实请求最终没有任何实际降档或输出替换。复杂代码、最终复核仍归 Codex；模块成功不等于减少了一次模型生成。 | 尚未解决；需要逐模块的替代场景及对照，不能仅加更多功能 |
| 2. 判档目标缺少可验证的下一步状态 | 路由输入是整体任务、最近公开进展和工具片段，没有经过验证的下一步动作/难度标签。标准主要按任务语义分档，未对不同模型、任务阶段及质量损失建立效果标定。旧版因此经常把复杂任务持续判高；v11 的上限只防止加价，并未让判档产生降档收益。 | 输入结构已核对；它贡献了多少延迟/误判尚未因子实验验证 |
| 3. 长复查间隔易被日常进展打断，普通无变化建议不会停止 | 本地复现：每次假判断都要求间隔 10，五条“原验证计划检查通过，继续同一计划”的自然语言进展却全部未被极窄的 routine 正则识别，最终判断 6 次、变档 0 次。v11 只在连续两次越界建议时停止；medium → medium 不会触发停止。真实 Sol 并发修复也判了 5 次、变档 0 次。 | 可复现，待修；不能简单取消失败/新任务触发，也不能盲目减少所有复查 |
| 4. 返回正文重复，可能越筛越长 | `select/search/filter_output` 同时返回 `context` 和 `items[].text`；`compact` 同时返回 `context` 和 `blocks[].content`。本地全保留样本的 11,649 字节原文被包装成 25,297 字节 JSON；交接报告的 `outputBytes=4,229`，实际返回 JSON 却为 8,542 字节。 | **本轮已修代码**：MCP/CLI 正文只在 context 返回一次，条目保留来源、ID、判断等元数据；内部完整结果与 recall 不变 |
| 5. 全保留时仍执行昂贵排序 | 选择器反复排序，每次比较又对文本重新分词并与已选择项比较。假判断排除网络后，40/80/160 条短证据分别耗时 53/350/2,847 ms。即使所有内容都放得下，也走完整排序。 | **本轮已修代码**：所有候选能放下时直接完整保留，并保持原顺序；部分预算选择的旧排名计算尚未优化 |
| 6. 筛选颗粒与语义阈值没有目标场景标定 | 日志按固定 30 行切块；旧事故样本有 8 块混合关键证据和背景行、10 块纯背景、1 个末尾空块。混合块应保留，但纯背景也没有被实际排除。0.9 是保守初始阈值，不是目标场景标定结果；不能通过随意降低阈值制造漂亮压缩率。 | 输入与历史结果已确认；单独归因于块大小、问题表述、全读指令或阈值还未验证 |
| 7. 自动接入覆盖比功能清单窄 | 自动过滤只支持原生字符串或很窄的单段 MCP 文本；含 structuredContent 的 MCP 输出不支持，code_mode/functions.exec 等也有显式跳过。真实项目当日历史包含 123 次 structured 跳过。Jev 的建议工具功能返回 `nativeToolsRemoved:false`，交接功能返回 `nativeHistoryChanged:false`。 | 是真实能力边界；不能声称普通桌面所有输出都被压缩、原生工具清单被裁剪或已消费 token 被回收 |
| 8. 接受的输入长度与实际能判断的长度不一致 | quality 接受 100,000 字符正文，但传输约束是每题 state+question ≤30,000 字节。31,000 字符正文配 2 条简单规则，本地复现实际调用 0 次，两条均 REQUEST_LIMIT 回退为 needs_review。没有假报通过，但助手仍多走一次工具再自己复核。 | 可复现，待修；必须提前检查可处理范围，跨段规则不能靠简单切片假装完成 |
| 9. 串行阻塞和连接成本仍存在 | 工具回调先 await 路由，再 await 自动过滤；过滤还可能分多个批次顺序请求。真实传输每次 spawn 新 curl，没有跨进程连接池；模型生成等待这条同步路径。Jev 模型自身的低延迟不能直接当作本地经代理到 API 的端到端延迟。 | 源码已确认；未测各段独立耗时，不能声称网络是唯一或最大根因。并发改造需先解决共享预算和过期结果问题 |
| 10. 原实验没有测完整的安装税，也不足以验证全部功能收益 | fixed 与 auto 都经过同一桥接层和原生 hooks；selectedCapabilityRoots 为空，禁用 code mode，并禁止读取 skills。它测的是隔离的路由/过滤对照，不包含插件技能引导下的全部辅助往返，也没有完全裸 Codex 对照。事故任务还强制先全读日志，不能代表正常先 rg 的工作流。 | 测量范围已确认；旧报告明确限制过范围，但此前不能据此把整套插件认定为效率验收完成 |

第 4 项仅计 **content 中一个 JSON 结果**，没有把服务器额外返回的 structuredContent 再计一次；宿主是否重复呈现这两个通道尚未验证。不能用模型外的字节数宣称精确 token 倍数。

第 7 项实时汇总来自两个项目的共享日志，跨任务、可能跨运行版本，不是当前会话专属；28 次 eligible 与 6 条结果记录不能用来计算失败率，早期版本未记录相同结果事件。

本次代码修改在仓库中完成；**尚未更新桌面安装副本**。不要求现在再重启一次来证明效率。路由输入、无收益停止机制、输入预检和真正的端到端基线仍需处理，不把上述两项局部修复称为整套优化完成。

## 应采用的处理顺序

1. **先降低额外工作**：按“能替代哪一步”限定每个模块的触发；没有替代的日常状态判断、重复阅读和重复 review 默认不应继续叠加。保持必要的正确性验证。
2. **再修核心路由**：对目标模型建立简单/复杂/失败恢复的独立难度样本；验证阶段识别和降档质量，再确定持有期、复查条件与无收益停止条件。不能为了出现降档数字强制降档。
3. **补正常桌面路径**：安全支持实际常见工具输出，给大型内容做明确输入预检；质量规则无法局部检查时，应保留 Codex 处理，不追加一个无效判断。
4. **最后验证净收益**：完全裸 Codex、只开适配层、路由、过滤、完整插件分组；相同质量标准、缓存/调用数/失败/未知用量都报告。固定普通任务之外，还要有确实适合批量分类筛选的任务。不能先承诺百分比再挑样本。
