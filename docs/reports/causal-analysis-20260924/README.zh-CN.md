# 为什么 JevPilot 没有同时大幅省 token 和加速

日期：2026-09-24。本次只重新分析已有轨迹、实现与实时官方/上游文档，没有新增收费测试，没有修改运行时策略。

## 结论

两类原因同时存在：我们先前的接入确实增加了不必要工作；同时，“把 Jev 加进 Codex 就应该让整体时间和 token 大幅下降”并非成立的通用前提。Jev 的优势需要真正替代大模型原本会做的工作。判档本身是额外工作，只有后续收益超过它的成本才划算。

现有证据不足以断定 Jev 在 Codex 中无用，也不足以证明我们的自动判档已创造稳定净收益。最新省下的 GPT token 伴随着更短的读取路径；需要相同工作流、关闭 Jev 的对照才能分离两者。

## 1. 官方宣传与当前产品测量的不是同一件事

[官方发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 将 193.6 倍速度、444.6 倍成本优势限定在特定 System One 工作流，并注明这些接近现实收益的较高端。对照 LLM 被要求输出兼容的结构化判断和概率，这比不给概率的判断更慢、更贵。官方还说明速度实验通常在美国西海岸运行。

当前 Codex 任务仍由 GPT 搜索、写代码、测试、解释。Jev 主要增加“下一步需要哪个档位”的决策，没有直接接管这些生成工作。官方的局部替代倍率不能作为整个开发任务的倍率。

假设原任务 100 秒，只有 10 秒工作能被 Jev 完全替代，替代部分即使加速 100 倍，理想总耗时也只是 90.1 秒；若另加 3 秒协调，变成 93.1 秒。这是示意算术，不是实测。

[Astra-Ares README](https://github.com/miuuyy/Astra-Ares#native-effort-changes) 明确说尚未测量实际工作负载的缓存命中率和相对固定档位的节省；其[验收说明](https://github.com/miuuyy/Astra-Ares/blob/main/docs/validation.md)也区分协议测试与质量/成本收益。

[jev-codex-router](https://github.com/0xNatoshi/jev-codex-router#measuring-what-it-served) 还会改变模型，其费用报告与全部使用 Astra/Sol 的假设对照比较，并声明反事实 token 数和任务质量没有实验测量。它的估算与我们的同模型、真实任务 A/B 不是同一口径。不能据此推断所有其他项目没有收益，但也不能把仓库数量当效能证据。

## 2. 哪些确定是我们的接入问题

上一轮 v17 的 12 次完整实测，各组 6 次：GPT token 增加 50,627，加 Jev 后增加 330,970，总耗时增加 39.023 秒。存在已观察到的多余 skill 阅读、额外筛选和原生读取重复。

一个具体例子：日志任务先精确搜索获得约 1,398 字符结果，之后又完整运行 Jev prepare，再执行本地模板排除。这是增加一道处理，没有有效替代已经完成的检索。读取完整 skill 还增加了一个工具边界。

修复前 GPT 差额的记账恒等式：

| 分量 | token 差额 |
|---|---:|
| 生成次数差对应的基准输入重复 | +15,270 |
| 初始输入差异在后续生成中重复 | +33,312 |
| 后续历史增长差异 | +4,462 |
| 输出差异 | −2,417 |
| 合计 | **+50,627** |

这些是严格相加的记账分量，不是每项的因果估计。原生 token 数不能把具体插件说明逐字独立归因。

先前最后几次有效降档被预算规则拦截、记录分块过粗、完整筛选预算不足，也属于我们的实现缺陷；已经修复。这些修复证明功能能正确工作，不自动证明经济收益。

## 3. 最新版本仍有可量化的固定开销

最新 8 次、4 对、两个任务的实测：

| 指标 | 裸 Codex | 当前候选 |
|---|---:|---:|
| GPT 总 token | 462,084 | 412,850 |
| GPT 输入 token | 457,101 | 408,281 |
| GPT 输出 token（含报告的推理 token） | 4,983 | 4,569 |
| 报告的推理 token | 99 | 56 |
| GPT 生成次数 | 21 | 22 |
| Jev 请求 | 0 | 16 |
| Jev 输入＋输出 token | 0 | 28,757 |
| 路由决策耗时之和 | 0 | 12.767 秒 |
| 原生实际改档 | 0 | 2 |
| 语义证据筛选操作 | 0 | 0 |
| 总任务时间 | 212.188 秒 | 220.737 秒 |

16 次决策中 12 次推荐 high、4 次推荐 low，其中 2 次 low 是沿用已有低档，只有 2 次 high→low。复查周期全部为 1/2 个工具边界。平均每次路由约 0.798 秒、每任务累计约 3.192 秒。反复确认 high 可以有质量价值，但在这个样本里它的直接省时机会有限。

代码在首步转发和后续 hook 中等待判档，所以这些调用在任务继续之前引入等待。决策耗时之和仍不等于可直接从墙钟扣除的因果惩罚：事件可能与并行工具重叠。把 220.737−12.767 算成“关闭 Jev 的任务时间”是不成立的反事实。

判档标准描述的是下一步难度，不是经数据校准的“本次调用预期能省多少时间/费用”。当前的调用上限、复用周期和无收益冷却只能限制浪费，不能保证每次付费判断值得做。不同模型的难度/档位收益也没有各自完成校准。

## 4. 降低推理强度没有命中主要 token 来源

裸组约 98.92% 的 GPT token 是输入。每次请求都带上前文，降低 effort 并不会直接删除这些输入。

报告的推理 token 仅 99，不足总量 0.03%；这是接口提供的计数，不能当作模型内部真实计算量的完整测量，更不能据此断言模型没有思考。但是它说明现有账本没有证据支持“本样本包含大量可直接削减的推理输出 token”。

最新 GPT token 减少 49,234 的记账分解：

| 分量 | token 差额 |
|---|---:|
| 多一次生成的基准输入重复 | +15,157 |
| 初始输入差异在各生成中重复 | +20,154 |
| 后续历史增长差异 | −84,131 |
| 输出差异 | −414 |
| 合计 | **−49,234** |

日志裸组先用 cat 读取整份文件，命令记录约 64,321 字符；插件组先读首尾，约 6,806 字符，再执行精确排除。这些是工具记录尺寸，不冒充模型逐字接收量；逐轮 token 也确实反映出第三次请求起历史增长不同。

因此目前观察更支持“少读无关材料减少历史增长”，不能归因于 Jev 分类：本轮筛选调用为零。插件提示可以改变 GPT 的检索策略，但同样的策略是否无需 Jev 也能获得收益，尚缺当前版本匹配对照。

加上 Jev 的 28,757 token 后，净少 20,477，约 4.43%。跨模型 token 相加只表示数量；不同价格下成本可能有不同变化。[官方 Jev 价格](https://docs.typesafe.ai/models)按输入计费、输出免费，不能把一个 Jev token 和一个 GPT token 当作相同金额或相同套餐额度。

## 5. 为什么仍然慢：已知部分与尚未查明部分

已知：四对中三对较快，但第二次日志任务从 50.899 秒变成 68.025 秒，多 17.126 秒，抵消了其他改善。

该任务路由总时间为 2.936 秒。一次“上一条用量通知→文件变更开始”的可见间隔为 43.099 秒，裸组对应为 32.152 秒，差 10.947 秒。这段间隔不在已记录的命令执行区间内，但包含生成、网络和事件交付等因素，当前轨迹无法继续拆开。

不能把这十余秒全部甩给 VPN、服务端排队或者低档推理。没有完整服务端计时，也没有同一轨迹多档位重复对照。Jev 网络等待是实际开销；生成路径和响应时间波动也是实测事实；两者各自造成多少最终差值，尚未识别。

最新输入缓存占比：裸组 81.63%，插件组 82.17%。本轮没有支持“整体缓存命中明显恶化”的汇总证据；旧版本发生过的缓存问题不能直接作为当前变慢的根因。前缀保留也不保证每次服务端命中。

## 6. 筛选为什么也未必带来净收益

筛选必须先读候选、发送问题、保留来源/不确定性、返回有效证据；必要时还要回读。若 GPT 已经能用一次精确搜索找到答案，额外 Jev 工作就是新成本。若先把全文显示给 GPT 再过滤，已消耗的输入也不会撤销。

当前 prepare 是为后续结果选证据，compact 是生成可恢复的交接内容；两者不是随时改写原生完整历史的保证。不能把一次返回正文的缩小比例当成整个会话压缩比例。

[官方重排示例](https://docs.typesafe.ai/cookbooks/rerank_typesafe)也是先用本地检索缩小候选，再对需要语义区分的候选评分。官方[能力边界](https://docs.typesafe.ai/model-jaggedness/jev-1.13)说明无关上下文、多层间接判断、数值精确性和生成需要额外处理。复杂代码任务的下一步档位并非一个天然容易、永远正确的原子判断。

## 7. 必须补的验证，才能判断是否值得继续推广

1. **分离工作流优化与 Jev 贡献。** 同一精简工具说明/检索策略下比较关闭 Jev、固定合理档位、仅路由、仅语义委派、两者开启。已有旧版分组实验每格一次，不能替代当前版本的重复对照。
2. **按任务类型验收。** 机械小任务考察几乎零额外调用；大规模语义候选考察准确率、漏证据、回读率及真替代的 GPT 输入；复杂修复考察质量与降档后的返工。不能只挑 Jev 最擅长或最不需要 Jev 的样本。
3. **校准净收益。** 先记录每种阶段在固定 high/medium/low 的质量、耗时和分类费用，再决定何时值得询问 Jev、何时复用。未变化不等于无用，改档次数多也不等于省；目标是质量合格后的总成本和完成时间。
4. **分别报告时间和成本。** 保留配对顺序、所有失败/重试、p50/p95、缓存/未缓存/输出、Jev 用量；不把接口 token 计数翻译成未经测量的订阅额度。服务等待需更细的客户端时间标记，仍不能伪造服务端归因。
5. **冻结后测试未见过的任务。** 目前反复使用修复回归样本，可能存在针对样本优化。使用新的、预先冻结的用例与独立质量判定，才能判断对正常用户是否有稳定收益。

这些是待验证方案，不是已经实现或通过的性能承诺。本次没有为追求漂亮数字关闭功能、降低验收门槛或继续消耗收费 API。
