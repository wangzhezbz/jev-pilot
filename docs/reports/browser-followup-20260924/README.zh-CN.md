# Chrome 网络复查与 Computer Use 六步实测（2026-09-24）

这是追加诊断，未宣布 Chrome 已恢复，也不是 GPT 整体任务的省时、省费证明。初次测试没有改动安装配置；随后实施的代理配置修复见文末。VPN、Chrome 设置和官方插件代码均未修改。

## 网络复查

旧报告 `../CHROME-NETWORK-DIAGNOSIS.md` 已记录明确的恢复验收：旧版插件补齐代理变量转发并重新加载后，TUN 关闭时成功打开 example.com 并点击至 IANA 页面。旧结论不能被本次超时推翻。

本次只读检查发现：

- 当前 Chrome 插件版本 26.917.62051，原生主机注册有效，扩展已启用；重装后会话初始化仍超时。
- 三个已运行工具进程（11436、12154、13480）均未观察到标准代理环境变量，父进程 11248 为 ChatGPT.app 自带 Codex；另一条 Jev 适配后的后台进程 14222 有 HTTP_PROXY / HTTPS_PROXY / NO_PROXY。没有建立具体请求与这三个进程的一一对应关系，因此这里只能认定存在代理传递缺口线索。
- 系统 HTTP/HTTPS 代理均启用。同一官方初始化地址的无认证传输对照：直连 5.005317 秒超时（curl 28、HTTP 000）；使用现有系统代理 0.428923 秒返回 HTTP 403。403 仅表示 TLS/HTTP 可达，不表示登录验证成功。
- 新版 Chrome 插件目录不存在旧版修复使用的 `.mcp.json`；旧修复针对 unified-computer-use 的 cua_repl，不能认定覆盖了当前宿主。

当前优先假设是新工具宿主没有继承代理，但尚未通过当前真实 Chrome 请求的修复前后对照确认。不得将此写成已修复，也不得将浏览器页面可联网或 Jev 可用写成控制通道可用。用户目前不能重启 Chrome，本轮没有重启。

## Chrome 失败记录

Computer Use 驱动 Chrome 的六步预设脚本成功一次，耗时 3.872 秒。随后旧 Jev 策略运行失败：首次判断约 0.605 秒、执行前复查约 0.063 秒、点击等待约 120.002 秒超时，总计约 120.736 秒。该次 Jev 调用已计入原始失败记录，不作为零成本或成功样本。官方 Chrome 扩展本轮没有完成页面任务，不能用 Computer Use 结果代替。

## 继续排查与已实施的配置修复

后续检查确认，当前桌面后台进程 11248 本身拥有全部八个代理变量，而它启动的 `node_repl` 子进程没有。实际 `mcp_servers.node_repl` 配置缺少 `env_vars`，且没有启用 Node 环境代理；当前工具执行无认证初始化地址请求同样约 5 秒超时。旧版 `cua_repl` 清单仍显示完整，解释了旧诊断为什么可能漏报。

已将兼容逻辑扩展到已识别的 macOS 桌面配置：补充八个代理变量名，并在该 MCP 服务的 `env` 内添加 `NODE_USE_ENV_PROXY = "1"`。配置已私有备份；全量 TOML 对比和原版 Codex `mcp get` 前后对比确认，仅这两处预期设置变化，原命令、参数、工具权限和其他配置保留。没有写入代理地址、凭据或 API Key。

这是官方配置能力的组合：[Codex MCP 环境变量配置](https://learn.chatgpt.com/docs/config-file/config-reference) 和 [Node 环境代理开关](https://nodejs.org/api/cli.html#node_use_env_proxy1)。本次实际捆绑 Node 为 24.21.0；产品保守支持已识别的 24.5+ 布局，未知配置保持原状。

验证结果：

- 279 项回归通过，566 个文件/139 个模块的项目检查通过。
- 隔离启动原版 Codex，创建不发起模型轮次的临时协议会话：它启动的真实 `node_repl` 子进程收到全部八个代理变量和 `NODE_USE_ENV_PROXY=1`。GPT/Jev 调用均为零。
- 相同捆绑 Node 启用代理后，无认证传输约 825.5 毫秒收到 403；仅表示线路可达。
- 当前桌面连接在内核重置后仍超时约 5 秒，说明旧 MCP 进程没有因此载入新环境。已请求正常停用/启用 Chrome 插件，尚未收到完成确认；没有退出 Chrome，也没有强杀现有工具进程。

当前状态是“本机配置已修复，新进程代理继承已验证，当前 Chrome 操作验收待重新加载”。源代码已更新在工作区，尚未据此发布一个已验收的新版本。证据见 `node-proxy-config-repair.json` 和 `node-proxy-process-probe.json`。


## 插件重新启用后的验收

用户确认已停用并重新启用 Chrome 插件后，再次检查：代理白名单和 Node 代理开关均保留，但工具宿主 PID 11436、12154、13480 与操作前完全相同，仍无代理变量。浏览器发现成功；`nameSession` 实际控制调用在宿主 20 秒截止时超时，宿主报告已重置内核，没有完成任何页面操作。

因此，插件开关不足以重新加载当前共享工具宿主。已修正上一阶段的操作建议：需要正常退出并重新打开 **Codex 桌面应用**，Chrome 无需退出。用户完成前不宣称当前 Chrome 已恢复。当前任务没有强杀进程、重启应用或改动用户标签页。证据：`after-plugin-reenable.json`。


## 桌面重启后发现配置被重建，补齐启动时序

用户正常重启桌面后，后台和工具进程均已更换，但桌面生成的 `node_repl` 配置再次缺失代理白名单与代理开关。说明一次性配置修复会被桌面重新生成覆盖，上一阶段关于“只要重启就可载入”的建议不完整。此时未重复进行已知会超时的 Chrome 操作。

修复已前移到 JevPilot 启动适配层：桌面生成配置之后、原版 Codex 读取配置并启动 MCP 子进程之前完成。仍使用原有 MCP 配置字段；没有修改官方二进制、身份校验、权限或新增 Codex 启动覆盖参数。网络诊断异常不阻止普通 Codex 启动，未知布局保持原样。新增文件已纳入安装哈希校验。

隔离验收连续两轮均通过：每轮模拟桌面重建无代理配置，并清空启动进程代理环境；实际运行 JevPilot 原生启动器、适配层、原版 Codex 和真实 MCP 子进程，均自动补齐配置并收到系统代理及 Node 代理开关。验证只创建临时协议会话，没有模型轮次和 Chrome 页面操作，不能代替当前桌面验收。结果见 `startup-regeneration-probe.json`。

过程中同时发现并修复了启动入口在符号链接目录下静默退出的问题，新增回归证明其实际启动子进程。最终 280 项测试通过。新本机安装版本：`0.2.0+codex.20260924201153`。当前桌面仍运行升级前的适配层；普通 Chrome 页面验收等待加载新版本。
